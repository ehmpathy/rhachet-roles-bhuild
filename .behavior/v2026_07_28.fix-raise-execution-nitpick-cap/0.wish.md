# wish: raise the execution-stone nitpick cap past its natural floor

radio task: ehmpathy/rhachet-roles-bhuild#303

## .what

on the execution stone's peer-review judge, raise `--allow-nitpicks` from `3` to `10`.

`--allow-blockers 0` stays exactly as it is. that is the hard gate, and it does not move.

## .why

the cap sits BELOW the floor the gate can ever reach, so it is unconvergeable by a driver.

two L3 reviewers each surface ~2 advisory nitpicks on any large mature artifact. the floor
is therefore 2N = 4, against a cap of 3. observed live on `ehmpathy/rhachet` route
`v2026_07_26.feat-keyrack-vault-aws-params`, stone `5.1.execution.phase0_to_phaseN`:

- both L3 reviewers reached **approved, 0 blockers** at i024
- the stone still blocked **3 rounds** on `nitpicks exceed threshold (4 > 3)`
- it passed only via a human `--as overruled` — for advisory nitpicks, zero blockers

the ledger: 25 healthy `blockers exceed threshold` rounds (real convergence), then 3 pure
nitpick rounds that no amount of work could clear.

**why a driver cannot converge it.** the nitpick reviewer is non-deterministic
(deepseek/v4-flash). to lower the count a driver must edit files — which busts the review
subject hash — which re-runs the reviewer — which surfaces a fresh batch. the fix and the
re-roll are the same action. a treadmill.

so the gate cannot be driven to pass. it can only be human-overruled, which defeats the
autonomous drive for an artifact that already carries zero blockers.

## .acceptance

- the execution-stone judge default carries `--allow-nitpicks 10`
- `--allow-blockers 0` is unchanged — prove it, do not assert it
- a stone with ≥1 blocker still fails. the reviewer can still block. demonstrate this
- a stone with 4 advisory nitpicks and 0 blockers now passes without a human overrule

## .why this is repair, not relaxation — read this first

`rule.forbid.self-grant-human-gates` names a raised `--allow-nitpicks` as a **forbidden
workaround**: it manufactures the pass that `--as overruled` exists to grant. this change
looks identical to that move. it is not, and the difference must survive in the record.

the test that brief gives: **after the edit, can the reviewer still block?**

- **yes** — blockers stay 0, so a real defect still stops the stone dead. that makes this
  repair: a gate whose cap was set below its own arithmetic floor was DEFECTIVE, and 10
  clears 2N while it still flags a genuinely nitpick-heavy artifact.
- what would make it relaxation: any move on `--allow-blockers`, or a cap raised because a
  specific verdict was inconvenient rather than because the gate was unreachable.

carry this rationale into the yield. a future reader who finds "we raised the nitpick cap"
with no stated reason will fairly read it as the forbidden move.

## .scope

the execution-stone judge default only.

the task names two deeper fixes — a deterministic nitpick reviewer (2), and a pass
condition of "approved + tracked follow-ups" rather than a raw count (3). **do not attempt
either here.** (3) in particular is the principled fix and deserves its own wish.

push a follow-on radio task for (2) and (3) before you arrive, so the debt is tracked
rather than lost behind the quick unblock.
