# vision: the execution gate becomes reachable again

> raise the execution-stone judge's `--allow-nitpicks` from `3` to `7`.
> `--allow-blockers 0` does not move.
>
> *(the wish proposed `10`; the wisher settled on `7` after the org-wide census below —
> deliberately tighter than the observed max, so the gate keeps real teeth.)*

---

## the outcome world

### day-in-the-life

a driver finishes an execution stone on a large, mature artifact. it runs
`rhx route.stone.set --stone 5.1.execution.from_vision --as arrived`.

the L1 reviewers converge over several rounds — real blockers, real fixes. then the two L3
enrolled reviewers each read the whole implementation and each return **approved, 0
blockers, ~2 advisory nitpicks**. total: 0 blockers, 4 nitpicks.

the stone passes. the driver moves to `5.3.verification`. no human is woken.

### before / after

| | before (cap 3) | after (cap 7) |
|---|---|---|
| 0 blockers, 4 nitpicks (the median-ish case) | **blocked** — `nitpicks exceed threshold (4 > 3)` | **passes** |
| 0 blockers, 7 nitpicks | blocked | **passes** — exactly at the cap; `>` is strict |
| 0 blockers, 8 nitpicks | blocked | blocked — genuinely nitpick-heavy |
| 1 blocker, 0 nitpicks | blocked | **blocked** — unchanged, the hard gate |
| cost of a zero-blocker stone | 1–3 wasted full-roster re-review rounds | 0 |
| worst case | a human `--as overruled` | drives itself |

### the aha moment

the value clicks when you stop asking "is the gate strict?" and start asking "**what does
this gate cost, and can effort reduce it?**"

every observed nitpick count on an execution stone exceeds the cap:

| route | observed counts | cap | outcome |
|---|---|---|---|
| `rhachet-roles-bhrain` / `fix-symlinks` | `4` | 3 | passed after **1** wasted round |
| `rhachet-roles-bhuild` / `fix-help` (this repo) | `7`, `6` | 3 | passed after **2** wasted rounds |
| `rhachet` / `keyrack-vault-aws-params` (per the wish) | `4` | 3 | **human overrule** after 3 rounds |

the reviewer is non-deterministic, so a lucky low roll is possible — and twice it arrived.
but a driver cannot **aim** for it: every edit that might reduce the count busts the subject
hash, re-runs the reviewer, and re-rolls the batch. **the fix and the re-roll are the same
action.**

so the gate is not unreachable. it is **unsteerable and expensive** — each round re-runs the
full 11-reviewer roster, including two enrolled sonnet reviews, on an artifact that already
carries **zero blockers**.

> a gate that opens only on a lucky roll is not a quality standard — it is a coin-flip,
> and every re-flip is billed to a stone that already passed the real gate.

## user experience

### who uses it

| user | goal |
|---|---|
| **driver** (the clone driving a route) | reach `passage = allowed` on a zero-blocker artifact without waking a human |
| **human foreman** | keep the hard gate (blockers) intact; stop being paged for advisory polish |
| **behaver** (`init.behavior`) | scaffold execution guards whose judge default is reachable |

### the contract inputs & outputs

the contract is the **judge line inside the execution guard template**, emitted by
`init.behavior` into every new route:

```yaml
judges:
  - $rhachet run --repo bhrain --skill route.stone.judge --mechanism reviewed? \
      --stone $stone --route $route --allow-blockers 0 --allow-nitpicks 7
```

inputs: `--allow-blockers` (unchanged, `0`), `--allow-nitpicks` (`3` → `7`).
output: the stone's passage verdict — `allowed`, or `blocked` with a reason string.

### what it looks like to leverage

```sh
# a driver scaffolds a route — the guard it gets already carries the reachable cap
rhx init.behavior --name fix-something

# ... work the stone ...
rhx route.stone.set --stone 5.1.execution.from_vision --as arrived
```

the driver never types `--allow-nitpicks`. it inherits the default from the scaffolded
guard. that is precisely why the default must be right: **it is the value nobody chooses.**

### the timeline

```
given  an execution stone whose peer reviews all reached approved
  and  0 blockers across every reviewer
  and  4 advisory nitpicks (2 from each L3 reviewer)
 when  the driver runs --as arrived
 then  the reviewed? judge passes the stone
  and  no human overrule is requested
```

```
given  an execution stone where one reviewer surfaced 1 blocker
 when  the driver runs --as arrived
 then  the judge blocks the stone
  and  the reason names the blocker threshold, not the nitpick threshold
```

## mental model

### how a user describes it to a friend

> "the nitpick cap was set to 3, but two reviewers always find two nitpicks each. so the
> lowest score possible was 4. the gate could never open on its own. we moved the cap above
> the floor."

### the analogies

- **a limbo bar under the floor.** you cannot get under it by ducking better. the bar is in
  the wrong place, and no amount of skill fixes that.
- **a thermostat set below absolute zero.** it will call for cooling forever.
- **a treadmill.** to lower the count you edit files → the subject hash busts → the
  non-deterministic reviewer re-runs → a fresh batch of nitpicks appears. the fix and the
  re-roll are the *same action*, so effort does not move the number.

### our terms vs theirs

| we say | they say |
|---|---|
| `--allow-nitpicks` threshold | "the polish limit" |
| `--allow-blockers 0` | "the real gate" |
| unconvergeable gate | "impossible to pass" |
| natural floor (2N) | "there's always at least four" |

we should keep our terms in code and use theirs in the yield prose — the arithmetic framing
(*floor* vs *cap*) is what makes this legible as a repair.

## evaluation

### how well it solves the goal

| goal | solved? |
|---|---|
| a zero-blocker execution stone passes autonomously | ⚠️ mostly — `7` clears the median (~5–6) and ~20 of the ~25 observed counts, but `8`/`9`/`13` routes still block |
| the hard gate survives | ✅ `--allow-blockers 0` untouched |
| a genuinely defective artifact still blocks | ✅ any blocker blocks; ≥11 nitpicks still blocks |
| human attention conserved | ✅ removes a per-stone overrule |

### pros

- **one-line change per template**, no new mechanism, no new code path
- reversible cleanly — if `7` proves wrong, it is a number edit
- keeps the nitpick gate *alive* (it still fires above 7) rather than a deletion — and at
  `7` the gate retains real teeth, since ~5 of the ~25 observed routes would still trip it
- unblocks routes today while the principled fix (a pass-condition rework) is scoped separately

### cons

- **`7` is a deliberate partial fix, not full coverage.** the execution guard declares
  **11 peer reviewers** (9 at level 1, 2 at level 3) and the judge sums nitpicks across all
  of them, so the reachable range is far wider than the cap. against the observed sample
  (`4–13`, median ~5–6), `7` clears roughly 20 of ~25 counts — the `8`, `8`, `8`, `9`, and
  `13` routes would **still block**. that is the accepted tradeoff: the wisher chose teeth
  over coverage, so a genuinely nitpick-heavy artifact is still stopped.
  the consequence to own honestly: this does **not** eliminate the human overrule, it makes
  it rarer. the cap remains coupled to reviewer count — the underlying design smell, and
  precisely what a roster-invariant pass condition (task item 3) would cure.
- it treats the symptom. the real defect is "a raw count as a pass condition for advisory
  findings." this wish explicitly defers that (task item 3).
- it looks, on a naive read, exactly like the forbidden self-grant move. mitigated only by
  the record we leave.

### edge cases & the pit of success

| edge case | how the contract keeps us safe |
|---|---|
| a real defect appears | it is a **blocker**, and `--allow-blockers 0` is untouched — the stone dies |
| a reviewer malfunctions (unparseable stdout) | unchanged — malfunction is its own terminal verdict, not a count |
| a genuinely sloppy artifact | 11+ nitpicks still blocks; the gate is loosened, not removed |
| someone later nudges `--allow-blockers` | this vision states the invariant explicitly so the diff reads as a violation |
| the other stones' caps drift | out of scope by design — blueprint stays `3`, verification stays `0` |

## why this is repair, not relaxation

`rule.forbid.self-grant-human-gates` names a raised `--allow-nitpicks` as a **forbidden
workaround** — the driver manufacturing the pass that `--as overruled` exists to grant.
this change is shaped identically. the difference must survive in the record, so:

**the test that brief gives: after the edit, can the reviewer still block?**

**yes.** `--allow-blockers 0` is untouched. one blocker from any reviewer kills the stone.
the reviewer's power to stop bad work is intact and unreduced.

that is what makes this **repair**:

- the cap (`3`) sits **below every observed count** (`4`, `6`, `7`) on a mature artifact, and
  no action available to a driver moves the count toward it — every attempted reduction
  re-rolls the reviewer. a pass condition reachable only by luck, never by effort, is a
  **defect in the gate**, not a strict standard.
- `7` restores steerability for the common case while keeping the gate live — it still
  flags a genuinely nitpick-heavy artifact, and by design still blocks the worst observed
  routes rather than waving everything through.

**stated precisely, because the flattering version is the tempting one:** the gate is not
impossible. two ledgers show it cleared without a human. what it does is bill **1–3 wasted
full-roster re-reviews** to a stone that already carries zero blockers, on a coin-flip that
effort cannot weight — with a human overrule as the worst case rather than the rule. that is
a defect for a gate whose whole purpose is to be satisfied by good work, and it is the claim
we can defend against our own evidence.

what would make it **relaxation** instead:

- any movement on `--allow-blockers`
- raising the cap because one *specific verdict* was inconvenient, rather than because the
  gate was structurally unreachable

we are doing the first, not the second. **a future reader who finds "we raised the nitpick
cap" with no stated reason will fairly read it as the forbidden move — so the reason must
ship with the change**, in the yield and in the commit.

exercise this explicitly (two reviewers, 2 nitpicks each, expect a count of 4) rather than

these artifacts persist in the route regardless of the cap. so raising the cap **loses no
signal** — the nitpicks remain on disk and reviewable — it only stops them from *blocking*.
the conclusion A5 supported survives; its stated mechanism was wrong.

## scope boundary

**in scope:** the execution-stone judge default, in **both** variants
(`from_vision`, `phase0_to_phaseN`), plus the snapshot and the tests below.

### "prove it, do not assert it" requires two tests, not one

the wish demands that `--allow-blockers 0` be **proven** unchanged, not asserted. that rules
out the cheap version of this test, so both of these are required:

| test | proves | why it alone is insufficient |
|---|---|---|
| **template-read** (the `[t10]`/`[t11]` pattern) | the cap moved on *every selectable variant* | it only proves a **string is present**. that is an assertion, which the wish forbids by name |
| **behavioral** | a reviewer that emits a blocker still stops the stone; 4 nitpicks + 0 blockers now passes | it cannot cheaply cover every variant, which `guard-variant-consistency` requires |

the template-read test satisfies `rule.require.guard-variant-consistency`; the behavioral
test satisfies "prove it." neither substitutes for the other.

**a cost note for execution:** the only extant behavioral harness is the full-journey fixture
in `skill.init.behavior.guards.acceptance.test.ts`, which does a `pnpm install` and links
five roles per run. the reviewer stubs (`review.sh`, `enroll.sh`) emit their counts from
shell, so **the counts are an input variable** — both criteria can be exercised without a
second full install. settle the shape at execution; the point here is that a naive approach
doubles a heavy fixture.

### this route's own guard stays at `3` — deliberately

`.behavior/v2026_07_28.fix-raise-execution-nitpick-cap/5.1.execution.from_vision.guard:222`
was stamped from the template *before* this fix, so **this route is itself gated at the
defective cap.** its own execution stone will likely block on `4 > 3`.

we leave it. to edit the guard that gates the stone we are currently judged by **is** the
self-grant move, whatever rationale we attach — the template edit changes a default for
future routes where we are not the subject; a route-copy edit changes the gate on our own
work, to our own benefit, right now. same diff, very different act.

the consequence is a feature: a block at `4 > 3` here is a **third independent observation**
of the defect, produced by the work that repairs it. the overrule it forces is the final
datapoint, not an embarrassment.

**explicitly out of scope**, per the wish:

## what is awkward?

**this change is indistinguishable from the forbidden move by inspection alone.** the diff
is literally "driver raised the nitpick cap." only the *reason* separates repair from
self-grant, and reasons live in prose, which rots. we are relying on a yield and a commit
message to carry a distinction the code cannot express. that is genuinely uncomfortable.

**the cap is still coupled to reviewer count.** `7` encodes an assumption about reviewer
roster size into an unrelated knob. add a third L3 reviewer and we are a step closer to the
wall again, with no signal that we are. a pass condition of "all reviewers approved" would be
invariant to roster size — exactly why task item (3) is the real fix and this is the stopgap.

**and `7` does not clear the observed range.** it sits below the `8`, `9`, and `13` counts
already on record, so those routes still block and still need a human. this is intentional —
teeth over coverage — but it means the change **reduces** the overrule rate rather than
eliminating it. a reader who expects the problem to be gone will be surprised; better to say
so here than to let them discover it.

**we are widening a gate to work around a non-deterministic reviewer.** the treadmill exists
because the reviewer re-rolls on every edit. the honest fix is determinism (task item 2);
widening the gate makes the treadmill tolerable rather than removing it.

**the blueprint stone has the same latent defect and we are walking past it.** scope
discipline says leave it. it still feels like shipping half a repair.

**the tradeoff we accept:** an imprecise number that unblocks routes today, with the
principled fix tracked as debt — rather than a correct fix that leaves every mature
execution stone waiting on a human.
