# vision — radio push and drain fall back to the ambient credential (#513)

## the outcome world

a push or a drain with no `--auth` just delivers. the ehmpath bot token goes first. where it is
absent, or github refuses it, the same send goes out under the credential the box already holds,
and one line says so.

| | before | after |
|---|---|---|
| grove, bot token expired | 401, record held, nudge to re-run `--auth as-human` — which strips `GITHUB_TOKEN` from the env, so it fails too on a grove with no gh login | resent under `GITHUB_TOKEN`; delivered; one line |
| laptop, bot token never set | keyrack-absent nudge; human re-runs with `--auth as-human` | delivered via the gh login; one line |
| held record from a prior absent-token push | waits until a human drains with `--auth as-human` | the next push or drain delivers it |
| `--auth <x>` passed on purpose and refused | held, fix named | unchanged — never past a chosen auth |

**the aha:** no seat types `--auth as-human` again. the fallback is a property of the default,
so the one place a caller *chose* an auth is the one place it never fires.

## the contract

**when the fallback fires** — all three hold:
1. the chosen auth is none: no `--auth` on the push, the record's stored auth is null, no `drain --auth`
2. the bot token is absent (keyrack non-granted), or a send under it fails `upstream:401` or `upstream:access`
3. an ambient credential is present

**the ambient credential**, first present wins — the order gh itself reads:
`GH_TOKEN` env → `GITHUB_TOKEN` env → the gh login (`gh auth token`).
it resolves to an explicit token, so the send path that strips env tokens stays as is.

**the line**, once per distinct (credential kind, reason) pair in a push or drain that delivered under ambient — in practice one:
```
🦫 delivered via the <GH_TOKEN env | GITHUB_TOKEN env | gh login>; <the ehmpath bot token was absent | github refused the ehmpath bot token (401|403)>
```
a kind and a reason — never a token value.

**the fail**, when ambient is absent or refused too: a `ConstraintError` that names both
credentials, each with its fix — and, where ambient was refused, which source (`GH_TOKEN env`,
`GITHUB_TOKEN env`, `gh login`) github refused; the record held `upstream:auth` (or the refusal's reason), as
today.

**the seam:** push and drain both send through `setRadioTaskRecordUpstream`
(`src/domain.operations/radio/record/setRadioTaskRecordUpstream.ts:48`) → `getOneRadioContextForRecord`.
the fallback lives there once, so the drain takes it for free (done-means 2).

## mental model

"it tries the bot first, then uses whatever you're logged in as, and tells you which." — the same
shape as gh's own precedence, with the bot token placed ahead of it.

| we say | a seat says |
|---|---|
| ambient credential | my gh login / the grove's token |
| bot token refused | the bot token expired |
| chosen auth | I passed `--auth` |

## evaluation

- **goals:** case 2, 3, 4 deliver with no `--auth`; case 6 keeps an explicit choice binding;
  case 5 fails loud with both fixes. every done-means bullet maps to a case
- **pro:** one seam for push + drain; no queue order or set-aside change (#511 untouched)
- **pro:** a resend never doubles — delivery reuses the upstream findsert, which matches the
  exact title from an issue list (`daoRadioTaskViaGhIssues.ts:118-157, 242-249`). precondition:
  the ambient credential can read the target's issues, so it sees a create the bot attempt made.
  execution clamps it: a stub gh that refuses the bot after its create, then asserts one issue
- **con:** a refused bot token now costs one extra send round trip before the ambient send
- **con:** a task may land under a human's identity where the bot was intended. the wish asks for
  exactly this; the line makes it visible on every such send
- **pit of success:** the fallback can never fire past a chosen auth, and can never fire for a
  stored auth the replay guard refuses (`isRadioRecordAuthReplayable.ts`), so it opens no new
  path for a planted record to run a shell or leak a secret var

## open questions & assumptions

- **[answered]** which 403s count as "refused"? → the write refusals the classifier already
  names, `upstream:401` and `upstream:access` (`asRadioUpstreamReason.ts`). a 403 rate limit /
  abuse detection classes as `upstream:rate-limit` first, and stays a halt, never a fallback
- **[answered]** may a test reach the real gh login? → no. the gh-login source is skipped in a
  test env, as `--auth as-human` is today (`getGithubTokenByAuthArg.ts:50-52`); env sources still
  apply, read from the injected `context.env`
- **[answered]** how many lines? → one per distinct (credential kind, reason) pair per push or
  drain; in practice one. mirrors the extant `drain --auth` notice (`asRadioDrainAuthNotice.ts`)
- **[answered]** where does the line print? → both clis print from record fates
  (`radioTaskPush.ts:230-237` via `asRadioPushOutput`; `radioTaskQueue.ts:270` for the drain
  notice). a delivered fate carries the credential kind + reason, and each cli derives the line
- **[answered]** does a fallback write back? → no. the record's stored auth stays null, so the
  next send tries the bot token first, once fixed
- **[answered]** what does `gh auth token` do with no login? → unstated by its manual; the derive
  reads non-zero exit or empty stdout as absent, correct under either behavior
- **[wisher]** `GH_TOKEN` as an ambient source, ahead of `GITHUB_TOKEN`? the wish names only the
  gh login and `GITHUB_TOKEN`. best guess: include it — it is gh's own top precedence, so radio
  reads what `gh` reads on the same box. clean rework (one line) if unwanted; does not block
- **[answered]** `radio.task.pull`? → out of scope; the wish names push and drain only
- no **[research]** items remain; the one **[wisher]** item is a clean rework and does not block

## groundwork

### external research

- gh cli credential precedence, verified at https://cli.github.com/manual/gh_help_environment:
  `GH_TOKEN` and `GITHUB_TOKEN` ("in order of precedence") take "precedence over previously
  stored credentials". the fallback reuses this order
- `gh auth token`, verified at https://cli.github.com/manual/gh_auth_token: "outputs the
  authentication token for an account on a given GitHub host" (active account, default host).
  ⚠️ the manual does not say what it does with no stored login, nor whether it echoes an env
  token. so the ambient derive runs it with `GH_TOKEN`/`GITHUB_TOKEN` stripped, and reads a
  non-zero exit or an empty stdout as "no gh login" — correct under either behavior

### internal research

- default auth: `RADIO_AUTH_DEFAULT = 'as-robot:via-keyrack(ehmpath)'` (`src/domain.operations/radio/auth/RADIO_AUTH_DEFAULT.ts:6`)
- token resolution: `getGithubTokenByAuthArg` → `genAuthFromKeyrack`; every non-granted keyrack
  status throws `ConstraintError` with `getKeyrackAuthFailureMessage` (`genAuthFromKeyrack.ts`)
- the gh boundary strips `GH_TOKEN` + `GITHUB_TOKEN` and sets `GH_TOKEN` only from an explicit
  token (`src/access/daos/daoRadioTask/runGhCommand.ts:30-41`) — why `--auth as-human` fails on a
  grove that holds only `GITHUB_TOKEN`
- a 401 at the gh boundary → `ConstraintError` via `isGithubAuthFailure` + `getGithubAuthFailureMessage`
  (`runGhCommand.ts:68-77`); classified `upstream:401` / `upstream:access` by
  `asRadioUpstreamReason.ts`; a `ConstraintError` is a fault, not a refusal, so the record holds
  (`isRadioReplayRefusal.ts`)
- the stored-auth replay guard: `isRadioRecordAuthReplayable.ts`; auth shown to a reader:
  `asRadioAuthShown.ts`
- test pattern: a stateful stub `gh` first on PATH
  (`src/domain.operations/radio/task/push/setPartRadioTask.via-gh-issues.stub.integration.test.ts:20-22`)
- output vocab: `🦫` lead for radio notices (`asRadioDrainAuthNotice.ts:22`), `✋ ConstraintError:` for caller-fix faults

## what is awkward?

- the fallback lives in two moments — before the send (bot absent) and after it (bot refused).
  one orchestrator must own both, or the line and the fail will drift between them
- `--auth as-human` keeps its env-strip semantics (gh login only), so it stays narrower than the
  ambient fallback. a seat could find "no `--auth`" delivers where `--auth as-human` does not.
  left as is: the wish bounds this to the default path, and widening `as-human` would change an
  explicit choice
