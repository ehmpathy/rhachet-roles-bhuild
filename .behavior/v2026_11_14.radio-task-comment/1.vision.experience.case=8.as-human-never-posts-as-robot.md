# case=8 — an as-human comment never posts as the robot

feel · care: sharp · alterpath (inventory row 36). chosen alterpath: #406 names this guarantee
explicitly, and its failure is a reputation harm — a comment signed by the wrong identity.

## .narrative

the robot app may not post on `sandpine/infrastructure` (the org has not installed it). a clone
that a human sponsors pushes the note under the human's own gh login:

```sh
cat note.md | rhx radio.task.comment --via gh.issues --into sandpine/infrastructure --exid 31 --comment @stdin --auth as-human
```

the clone's shell happens to hold a `GH_TOKEN` (the robot's, from an earlier step). had the post
read that env, the comment would carry the robot's name while the clone reports it posted as the
human. the send clears `GH_TOKEN` and `GITHUB_TOKEN` for the gh call, so gh falls back to the
human's session: the comment lands as the human, as asked.

held under a shut gate, the record keeps `auth: as-human`; `radio.task.queue get` shows it, so
the human who later drains it sees whose name the comment will carry.

## .bdd sketch

```
given('[case8] an open gate; GH_TOKEN holds a robot token in the env')
  when('[t0] a comment is pushed with --auth as-human')
    then('the gh call runs with neither GH_TOKEN nor GITHUB_TOKEN in its env')
    then('the record holds auth as-human')
given('[case8b] a shut gate')
  when('[t0] the same push')
    then('queue get shows the held comment with auth: as-human')
```

note: as-human cannot run inside the test env (`getGithubTokenByAuthArg` forbids it under
`NODE_ENV=test`), so the proof in verification is the env the stub gh receives, not a real login.
