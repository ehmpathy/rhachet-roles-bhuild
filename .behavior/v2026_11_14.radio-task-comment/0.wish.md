## the primary ask — ehmpathy/rhachet-roles-bhuild#567 (verbatim)

> **title**
> feat(radio): comment on an extant task, behind radio.uses
>
> ## the problem
> a clone that must comment on an extant issue or pr has no path through the radio. so a director built `gh.issue.comment`, a raw `gh issue comment` wrapper that never read `radio.uses`. on 2026-10-22 it posted on ehmpathy/rhachet-roles-bhuild#489 while global radio was blocked (open hours). any write path beside the radio is a way around the blocker.
>
> ## why is this a problem
> `radio.uses` is the commander gate on every github write. a gate that one write path checks and another skips is no gate.
>
> ## can we delete the requirement
> no. directors must amend extant issues (correct a cure, add a requirement). today the only sanctioned move is a new task, which splits one concern across two issues.
>
> ## what is owed
> - `radio.task.push` can add a comment to an extant task (gh.issues: an issue comment; os.fileops: an appended entry), e.g. `--exid <n> --comment @stdin`
> - it obeys `radio.uses` exactly like a new task: blocked -> held QUEUED, sent oldest-first by the next push that gets through
> - `radio.task.held` lists held comments beside held tasks
> - a clamp: with radio blocked, a comment push is held and sends naught (red without the gate check, green with it)

note: `radio.task.held` has since become `radio.task.queue get` (v0.24.0); the held list it owes
is the queue's `get`.

## the same ask, repeated — its extra contract (verbatim excerpts)

### ehmpathy/rhachet-roles-bhuild#533

> ```sh
> cat amendment.md | rhx radio.task.push --via gh.issues --into <owner/repo> --exid <N> --comment @stdin
> ```
>
> - appends ONE comment to task N; never reads, rewrites, or touches the body or title
> - recorded first into the route's `.radio/`, like every push
> - held under `radio.uses` like every push (a blocked comment is held QUEUED, delivered by the next push that gets through)
> - `os.fileops` channel: appends a comment record beside the task file
> - `--comment` with `--description` or `--title` = exit 2 (one act per call)
> - `--comment` without `--exid` = exit 2, with a fix that names `--exid`
> - idempotent under `--idem findsert`: the same comment body on the same task is not posted twice
>
> ## acceptance
>
> - an integration test on `gh.issues` (or its test double for the channel) proves, after `--exid N --comment @stdin`: the body of N is byte-identical to before, and exactly one new comment holds the input
> - a test proves a blocked `radio.uses` holds the comment and the next allowed push delivers it
> - a test proves the findsert re-run posts no second comment
> - `--help` shows the comment form with an example

### ehmpathy/rhachet-roles-bhuild#406

> - `--auth` the same modes as `radio.task.push` (`as-human`, `as-robot:via-keyrack(owner)`, …)
> - **idempotent** — an identical body already on the task is a `[KEEP]`, not a second post. an
>   agent that retries after a timeout must not double-post
> - **never** edits the task's body, title, or status
> - `as-human` unsets `GH_TOKEN`/`GITHUB_TOKEN`, so the post cannot land as a robot while the caller
>   believes it posted as themselves — `daoRadioTaskViaGhIssues` already does this for push
> - respects the `radio.uses` gate, as push does
