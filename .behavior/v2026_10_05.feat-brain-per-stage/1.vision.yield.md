# 1.vision · a behavior route picks its brain by stage

## the outcome world

### a day in the life

mara runs `rhx init.behavior --name feat-invoice-tax --size mini`. her clone drives. on `1.vision`
it switches to `claude-opus-5-5[1m]` and stays there through criteria, research, and blueprint.
the moment it enters `4.1.roadmap` it switches to `claude-sonnet-5-5[1m]`, and stays there through
execution, verification, and playtest. the claude peer reviewers that ran on `claude-sonnet-5[1m]`
now run on `claude-sonnet-5-5[1m]`. mara never typed `/model`.

### before / after

| | before | after |
|---|---|---|
| design stones | whatever brain the session started on | `claude-opus-5-5[1m]`, switched on entry |
| build stones | the same brain as design | `claude-sonnet-5-5[1m]`, switched on entry |
| the switch | a human remembers `/model`, or nobody does | the stone's guard does it |
| sonnet reviewers | `claude-sonnet-5[1m]` | `claude-sonnet-5-5[1m]` |
| other reviewers | their brain | their brain (unchanged) |
| a template edit that drops a brain | silent | a red test that names the template |
| an unenrolled driver (`claude` in a terminal) | drives every stone | halts at `1.vision` until it runs `rhx enroll claude --as @:driver --roles driver` |

### the aha

the brain moves at the one place the work changes kind — from *shape* to *build* — and nobody has
to remember to move it. the stones that decide the design get the stronger brain; the stones that
type it out run cheaper and faster.

## the contract

three changes to the template set, and one to the dep floor. no runtime code changes — bhrain does
the switch.

**1. every guard template declares a brain** (top-level key, under the provenance block):

| phase | guard templates | `brain:` |
|---|---|---|
| design | `1.vision.guard.{light,heavy}` · `2.1.criteria.blackbox.guard.heavy` · `3.2.distill.domain._.guard` · `3.2.distill.repros.experience._.guard` · `3.3.1.blueprint.product.guard.{light,heavy}` | `claude-opus-5-5[1m]` |
| build | `4.1.roadmap.guard` (new) · `5.1.execution.from_vision.guard` · `5.1.execution.phase0_to_phaseN.guard` · `5.2.evaluation.guard` · `5.3.verification.guard` · `5.5.playtest.guard` | `claude-sonnet-5-5[1m]` |

**2. a new `4.1.roadmap.guard`**, added to `mini.adds`. it holds only `brain:` — no reviews, no
judges — so bhrain passes it at once (note: `artifacts only`). without it, the roadmap would inherit
opus from the blueprint.

**3. every `enroll claude --model 'claude-sonnet-5[1m]'`** becomes `'claude-sonnet-5-5[1m]'`
(11 lines in 5 templates). no other reviewer line changes.

**4. the bhrain floor.** the dev dep sits at `0.39.2` (already bumped on this branch). the peer
floor rises from `>=0.30.4` to `>=0.39.0`: a pre-0.39 parser ignores a `brain:` line, so a consumer
on an old bhrain would init routes that never switch, with no warn (F9).

**phase rule:** a stone's phase is its place. prefix `1.`–`3.` = design; `4.`–`5.` = build.
`0.wish.md` is the route's input, not a stone — the human writes it before any drive, so no brain
attaches to it. the wish's "wish" stage is met by the human, and `1.vision` is the first stone a
brain drives.

**inheritance:** an unguarded stone keeps the prior stone's brain (bhrain's sticky rule). every
unguarded stone in today's set sits after a guard of its own phase, so it lands right.

**re-dispatch:** bhrain dispatches a guard's `brain:` on every entry and never compares first. a
guarded stone whose brain already matches gets the same `/model` again; a switch keeps the
conversation, so the repeat is benign.

**reach:** bhrain needs an enrolled driver to dispatch into. an unenrolled driver halts at every
`brain:` stone, every time (bhrain seed S8). this change puts a `brain:` on `1.vision`, so every
unenrolled session now meets that halt at the first stone (`case=6`, F8).

## mental model

- **to a friend:** "the route switches models for you — opus while it designs, sonnet once it builds."
- **analogy:** an architect draws the plans; a crew builds from them. you pay for the architect
  where the decisions are, not for the whole job.
- **their words vs ours:** they say "model"; bhrain says `brain`, and forbids `model` as the guard
  key (it warns and drops it). they say "the plan part" and "the code part"; we say design stones
  and build stones, split at the blueprint.

## evaluation

### how well it meets the wish

| wish clause | met by |
|---|---|
| stones through the blueprint on opus | design guards declare opus; unguarded design stones inherit it |
| stones after the blueprint on sonnet | build guards declare sonnet; the new roadmap guard marks the switch |
| sonnet reviewers → sonnet-5-5; others keep theirs | an exact-string swap of `claude-sonnet-5[1m]` only |
| every size, no step after init | templates are the source; init copies them; the walk test covers all 5 sizes × 2 variants |
| tests prove each stone's and each reviewer's brain | the walk test (`case=5`, `case=9`) + the reviewer test (`case=10`): every claude lane names `claude-sonnet-5-5[1m]`, and every other lane reads as its baseline — the invariant c11b, which `case=10` guards |

### pros

- zero runtime code; bhrain owns the switch, its halt, and its render
- the switch sits at the exact place the work changes kind
- a cheaper, faster brain on the longest stones (execution is where most turns go)
- a template edit that drops a brain goes red

### cons

- one new file (`4.1.roadmap.guard`) exists only to carry a brain; the roadmap's pass note reads
  `artifacts only` instead of `unguarded`
- a model bump now means a sedreplace across 24 template lines — 13 `brain:` + 11 reviewer (pinned ids, by design)
- extant routes do not change
- an unenrolled session, today's common case, now halts at the first stone and must re-enroll once

### edge cases — and how the pit of success holds

| edge | what happens |
|---|---|
| a session resumes mid-design on sonnet, at an unguarded stone | it stays on sonnet until the next guarded design stone puts opus back (F1) |
| a human swaps the brain by hand | the next guarded stone puts the prescription back |
| the driver is not enrolled | bhrain halts at `1.vision`, names the cause, prints the `rhx enroll` fix; one re-enroll clears the route (`case=6`) |
| the brain rejects the slug | bhrain halts, names the cause and the fix (its own case 3) |
| a guarded stone whose brain already matches | bhrain re-dispatches the same `/model`; benign |
| an extant route | keeps its old guards (findsert); runs as before — no regression (F5) |
| a maintainer drops `brain:` or adds a guard with none | red test, names the template |
| a maintainer adds an unguarded stone | it inherits; the walk test confirms the phase brain |
| a consumer on bhrain 0.30–0.38 | its parser ignores `brain:`; routes init and drive with no switch. the raised peer floor warns at install (F9) |
| a `model:` key typed by habit | bhrain warns by name and drops it; the walk test also fails |

## what is awkward?

- **a guard whose only job is a brain.** `4.1.roadmap.guard` holds no review and no judge. "guard"
  reads as a gate, and this one gates naught. it is bhrain's shape — a brain lives on a guard — so
  we use it rather than invent a local one, as the wish asks.
- **inheritance is invisible in the files.** a reader of `3.1.3.research.*.stone` cannot see which
  brain it runs on; they must know the prior guard's. the walk test is what makes it checkable.
- **pinned ids drift.** `claude-sonnet-5-5[1m]` is right today and stale on the next release. the
  wish wants a pin ("the current sonnet, not an older one"), so the next bump is a deliberate edit.
- **a feature about cost now gates the common path.** the wish is about cheaper build stones; its
  most visible effect on an unenrolled session is a halt at the first stone. the halt is correct
  and teaches its fix, but it is a surprise this change introduces, not bhrain alone.
- **two kinds of "brain" sit in one guard.** `brain:` bounds the driver; `--model` on an `enroll`
  line bounds a reviewer. both move in this change, by different rules. a maintainer could conflate
  them.
