# case=005 — the yagni peer names the smaller change

> **who** — a driver clone at `1.vision`, with a design it has defended for eight rounds
> **came for** — to ship a design that satisfies the wish
>
> cell — `actor=driver · lens=yagni · feel=sharp · care=alterpath`
> — *(**fallback:** the extant `has-pruned-yagni` **self** slug catches the same bloat one stage
> later, at blueprint. `freq` common × `cost` low — what #354 buys is the earlier catch, not a
> capability that is otherwise absent. demoed anyway: it is the lens's whole payoff)*

## the narrative

my vision argues for a name-builder to contain an aliased env word. it is careful work. eight peer
rounds have shaped it, and every reviewer that read it graded coverage, hazards, or decomposition —
each asked whether i built it *well*. not one asked whether i should build it **at all**.

the yagni lane does, and it does not merely object. it names the smaller change:

```
🔴 1 blocker — yagni-and-simplicity
   the name-builder has one call site per name, and no second is named.
   the two extant functions are already the seam it proposes to create.
   the wish asks that the class be *audited*; a permanent enforcement
   mechanism is a scope leap beyond the ask.

   the smaller change that satisfies every stated criterion:
     change two words in getQueueUrlForTask.ts and its peer. audit, no guard.
```

three of its six checks killed the design independently — caller count, extant seam, and
audit-is-not-a-guard. i had no answer to any of them, because i had never been asked.

i take the smaller change. the design drops from a builder plus its tests to a two-word edit.

## the demo

```gherkin
given a 1.vision yield that proposes a name-builder abstraction
  and the builder has exactly one call site per name
  and the repo already holds two functions that serve as the same seam
  and 0.wish.md asks only that the class be audited

[t0] the extant lanes run — coverage, hazards, decomposition
  when each grades the design
  then each returns 0 blockers
   and no lane asks whether the component is owed at all

[t1] the yagni lane runs
  when it traces each component to an acceptance criterion in 0.wish.md
   and counts the call sites of each proposed abstraction
   and checks whether the proposed seam duplicates an extant boundary
  then it raises 1 blocker
   and the blocker names a concrete smaller change, never a bare objection

[t2] the driver takes the smaller change
  when the driver replaces the builder with a two-word edit to the two extant functions
  then every criterion in 0.wish.md is still satisfied
   and the yagni lane returns 0 blockers
   and the coverage lanes still return 0 blockers
```

## what this proves

- 🟡 **the gap is real and it is structural.** `has-pruned-yagni` exists as a self review at two of the
  seven behaver stages — blueprint and execution — and as a peer lane at none of the seven,
  `1.vision` included, which is where the design is chosen.
- the strongest form is a concrete alternative. `[t1]` demands the lane state the smaller change,
  so the driver receives a change to take rather than a bare claim to argue with.
- simplicity is not thinness. `[t2]` re-runs the coverage lanes, because a cut that drops an
  owed criterion is a worse defect than the complexity it removed.
