# case=2 — drop a stuck record, with a reason kept

feel: happy · care: critipath

## .narrative

the clone decides the #599 update is moot — the supersede note already landed. it runs
`radio.task.queue del --key 3f9a… --why "superseded by #605"`. the record leaves the queue. its
file stays on disk, marked DROPPED, its body and the reason beside it, so a human who disagrees
can read what was dropped — the `del` output names the file — and re-push it. no verb lists
dropped records in v1; `get` lists only what waits. the next drain does not see it.

## .timeline

```
given the queue holds [A] update #599 (set aside, upstream:access)

when [t0] radio.task.queue del --key <A>
  then ✋ ConstraintError: --why is required, exit 2
  then A is unchanged

when [t1] radio.task.queue del --key <A> --why "superseded by #605"
  then A's record reads recordStatus DROPPED, reason "dropped: superseded by #605"
  then A's title, description, auth stay on disk, unchanged
  then the output names the key, the label, the why, and the path of the record file
       (e.g. .behavior/.radio/record.<A>.json), so a human who disagrees can read it there
  then exit 0

when [t2] radio.task.queue get
  then A is absent from the list

when [t3] radio.task.queue drain
  then A is not sent

when [t4] radio.task.queue del --key <A> --why "again"
  then ✋ ConstraintError: record <A> is DROPPED, not held · exit 2

when [t5] radio.task.queue del --key 0000000000000000 --why "x"
  then ✋ ConstraintError: no record holds key 0000…; see the keys via radio.task.queue get
```
