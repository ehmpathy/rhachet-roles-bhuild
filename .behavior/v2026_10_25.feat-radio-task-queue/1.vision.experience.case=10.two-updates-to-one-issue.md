# case=10 — two updates to one issue wait in order

feel: sharp · care: critipath · found at 5.1 execution (r10 i006): a `DELIVERED` sent past its
set-aside `CLAIMED` is refused upstream ("cannot deliver unclaimed task") and closed for good

## .narrative

a fleet clone claims issue #599 in `sandpine/svc-bookings`, does the work, and pushes the
deliver. the robot may not write that repo, so both pushes sit in the queue: `claim #599`, then
`deliver #599`. the next push to another repo carries the backlog out. `claim #599` meets the
access fault and is set aside, named with its fix. `deliver #599` is not sent: an update to an
issue whose earlier update still waits goes after it, never past it. the drain shows it as a
wait, not a fault: "behind claim #599 on the same issue: unsent, sends once it lands or is
dropped", with no fix of its own. a deliver to another issue in the same repo still goes.

the clone runs `queue get`. the deliver row reads "waits behind <claim key> (same issue #599)"
and points to the claim's fix. a human amends the claim to as-human; the next drain sends the
claim, then the deliver, in that order. had the human dropped the claim instead, `del` would
say "1 update to #599 waits behind it; it sends next drain", and warn that the deliver needs a
claim: if #599 is not claimed upstream, the next drain refuses it for good. it names both fixes,
a re-push of the claim or a drop of the deliver too. `get` reads the deliver as "re-checked on
next drain", never as a live wait on a record that is gone.

## .timeline

```
given the queue holds, oldest first
  - [A] claim #599   → svc-bookings  (stub gh: not accessible by integration on edit)
  - [B] deliver #599 → svc-bookings
  - [C] deliver #600 → svc-bookings
  - [D] create       → svc-rentals
  and radio.uses allows both

when [t0] a carrier push drains them
  then A is set aside, upstream:access, with its amend + drop fix
  then B is held QUEUED, unsent, reason behind:<A key> (same issue #599), never refused
  then the drain row for B reads as a wait: no fault label, no fix lines
  then C is sent (it names another issue), and D delivers

when [t1] the clone runs radio.task.queue get
  then B reads "waits behind <A key> (same issue #599)", with a pointer to A's fix
  then B never reads "since opened" (that is gate words)
  and the stop line counts B as "behind an earlier update to the same issue", not a fault

when [t2] the human drops A: radio.task.queue del --key <A key> --why "claim moot"
  then the drop output says "1 update to #599 waits behind it; it sends next drain"
  then it warns "⚠️ the deliver of #599 behind it needs a claim; if #599 is not claimed
    upstream, the next drain refuses it for good", with two fixes:
    re-push the claim (rhx radio.task.push ... --exid 599 --status CLAIMED),
    or drop the deliver too (rhx radio.task.queue del --key <B key> --why "...")
  then get reads B as "not reached (was behind <A key>, no longer held; re-checked on next drain)"
  and if neither fix is made and #599 is unclaimed upstream, the next drain refuses B
    ("cannot deliver unclaimed task"): closed, named once by that drain, exit 2

given instead [t2'] the human amends A to as-human, and drains
  then A lands, then B lands, in that order

given instead A is held at a shut gate
  then B is not held behind A: the same repo meets the same gate, so B is held at that gate
  with its own gate reason, never overwritten by a behind reason
```
