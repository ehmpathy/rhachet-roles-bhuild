# case=3 — `as-ehmpath` prefers keyrack; `via-keyrack` never leaves it

feel: happy (+ one sharp alterpath) · care: critipath (the common case; keyrack is the robot's home)

## .narrative

a clone on a provisioned box pushes with `--auth as-ehmpath`. keyrack grants the beaver token; the ambient spot is never read. behavior matches today's default, `as-robot:via-keyrack(ehmpath)`.

when a mechanic debugs keyrack and types `--auth as-ehmpath-via-keyrack` on a box whose keyrack is locked, the push is held and the miss names keyrack alone — no fall-through hides the keyrack fault, even though the box's ambient login would have worked.

## .timeline (sketch)

```
given('a box whose keyrack grants EHMPATH_BEAVER_GITHUB_TOKEN for ehmpath, env prep')
  when('[t0] rhx radio.task.push ... --auth as-ehmpath')
    then('the keyrack token is used')
    then('git config and gh auth token are never read')
    then('the issue is created; the output adds: auth = as-ehmpath (via keyrack)')
given('a box whose keyrack is locked, and whose ambient email is ehmpath with a gh login')
  when('[t1] rhx radio.task.push ... --auth as-ehmpath-via-keyrack')
    then('exit 2; the push is held QUEUED (upstream:auth)')
    then('the fault reads:')
      └─ fix it: ✋ ConstraintError: --auth as-ehmpath-via-keyrack found no ehmpath token
         ├─ checked
         │  └─ keyrack: not granted (status: locked)
         ├─ unlock the robot token: rhx keyrack unlock --owner ehmpath --key EHMPATH_BEAVER_GITHUB_TOKEN --env prep
         └─ or let the ambient login pay: --auth as-ehmpath
    then('git config and gh auth token are never read')
```
