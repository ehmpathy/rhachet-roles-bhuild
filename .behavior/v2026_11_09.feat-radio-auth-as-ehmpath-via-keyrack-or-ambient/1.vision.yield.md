# 1.vision — radio `--auth as-ehmpath`: keyrack, then an ehmpath ambient login

## .the outcome world

### before

a radio send has one robot path: `as-robot:via-keyrack(ehmpath)`. a box with no unlocked keyrack — a fresh clone box, a yubikey-gated vault with no terminal — has two choices: fail, or `--auth as-human`, which sends under whoever is logged into gh. on the clone's own box that login IS an ehmpath account, but the skill cannot know it, so the clone must type `as-human` — a label that lies about who sends.

### after

| value | finds the token |
|---|---|
| `as-human` | the ambient gh login, as today. not renamed |
| `as-ehmpath` | keyrack first; on a miss, the ambient gh login, only if `git config user.email` is an ehmpath email |
| `as-ehmpath-via-keyrack` | keyrack only |
| `as-ehmpath-via-ambient` | the ambient gh login only, under the same ehmpath-email bar |

`as-robot:*` and the no-`--auth` default keep their sense (F3).

"keyrack" here is the coordinate the default already reads: owner `ehmpath`, env `prep`, key `EHMPATH_BEAVER_GITHUB_TOKEN` — so `as-ehmpath-via-keyrack` sends exactly as `as-robot:via-keyrack(ehmpath)` does. "ambient" is the effective git config of the repo the skill runs in (repo-local over global), plus the gh login of the host.

### a day in the life

a clone on a fresh box pushes `--auth as-ehmpath`. keyrack misses; the ambient email is the clone's ehmpath address; the gh login's token sends the task. the same command on bert's laptop refuses, and says why: keyrack locked, ambient email `bert@example.com`. bert unlocks keyrack, or types `as-human` on purpose.

### the aha

**one value, `as-ehmpath`, means "send as the robot, wherever the robot's token lives — and never as a human."** the label now tells the truth on every box.

## .the contract, sketched

### the miss — names each spot, what it held, and the fix

an auth fault already renders as a held push: `status = QUEUED (upstream:auth)`, then `fix it:` with the ConstraintError's message, then `amend it:` (`src/contract/cli/__snapshots__/radioTaskPush.integration.test.ts.snap`, case6–case10). the miss is that same block; only the message is new:

```
   ├─ status  = QUEUED (upstream:auth)
   └─ fix it: ✋ ConstraintError: --auth as-ehmpath found no ehmpath token
      ├─ checked
      │  ├─ keyrack: not granted (status: locked)
      │  └─ ambient: git config user.email = bert@example.com, not an ehmpath email
      ├─ unlock the robot token: rhx keyrack unlock --owner ehmpath --key EHMPATH_BEAVER_GITHUB_TOKEN --env prep
      └─ or send as yourself, on purpose: --auth as-human
```

other ambient rows: `ambient: git config user.email unset` · `ambient: ehmpath email, but gh holds no login (run: gh auth login)`. `via-keyrack` lists only the keyrack row; `via-ambient` only the ambient row. a miss exits 2 and the push is held, never lost.

### the hit — names the source, for `as-ehmpath` only

today a successful send prints no auth line. `as-ehmpath` alone has two possible sources, so its hit adds one line — `auth = as-ehmpath (via keyrack)` or `(via ambient)` — so a reader knows which spot paid. every other value's output is unchanged.

### the tests — no real gh login, ever

every test that reaches the ambient path puts a stub `gh` (and a stub-controlled git identity) on the PATH the **subprocess** runs under. `shx` inherits `process.env` and takes no env of its own (`src/infra/shell/shx.ts`), so a stub set on a context env never reaches it — the defect that let a real token reach a log in the prior draft. unit tests inject a fake `shx` and never exec.

## .mental model

- to a friend: "`as-ehmpath` sends as the robot. it looks in keyrack, then at the box's own login — but only if the box says it's an ehmpath box."
- analogy: a company card. check the wallet (keyrack), then the desk drawer (ambient) — and only take the drawer's card if the badge on the desk is a company badge.
- their terms vs ours: users say "robot token" / "my login"; we say keyrack / ambient. the help text pairs each value with where it looks.

| goal | met by |

| `--help` shows all four | case 6 |
| no test reaches a real gh | stub gh on the subprocess PATH; case 7; forbidden row 22 |

pros: one truthful robot label across boxes · additive — no extant value changes · the bar is a check the skill makes, not a habit the human keeps.

cons: two rosters of ehmpath identities (here and the peer) can drift (F6) · git config email is a weak identity signal — it is a self-declared string, not a verified one.

### pit of success

- a human's box never sends under the robot label: the email bar refuses first
- `via-keyrack` never falls through, so a keyrack fault is never masked
- an unknown value lists every value, the new three included

## .groundwork

### external research

- `gh auth token` prints the active host's token and exits non-zero with no login (gh cli manual, cli.github.com/manual/gh_auth_token). ⚠️ not run here: `gh auth token` is not a paved command on this box, and a real call would print a real token. the contract enters only through a stub gh in tests, so execution must pin the stub to this documented shape
- `git config user.email` exits 1 when the key is unset (git-config docs: "the section or key is invalid (ret=1)") — a "none set" cell, never a fault

## .what is awkward?

- the ambient token comes from gh, but the identity bar reads git config. a box can carry an ehmpath email and a human's gh login; `as-ehmpath` would then send under the human's token with the robot's label. the wish names the email as the bar, so the vision holds to it; a stronger bar (match the gh login against the roster) is a follow-up, not this wish
- `as-human` and `as-ehmpath-via-ambient` read the same gh login; only the label and the email bar differ. that is the point, but a reader may ask why two values reach one token
- the roster lives twice (F6)
