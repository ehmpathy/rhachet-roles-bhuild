# vision — a permanent refusal parks its own radio task

## the headline

**the wedge the wish describes is already cured on main** by #605 (merged 2026-10-31, v0.24.0).
an access refusal reads as `upstream:access`, which sets that one record aside; only a rate limit
or an outage halts the drain. every measured wedge (#511, #551, #591) predates that release, so
the fleet trees that wedged ran an older install. ⇒ F1: this route cites and proves the cure, and
builds the one outcome main still lacks — **`get` shows the refusal in github's words**.

## the outcome world

### before (an install older than v0.24.0)

a clone pushes a task. the radio replays the held backlog, oldest first. the head is an edit of
ehmpathy/rhachet#673 the bot cannot sign: `GraphQL: Resource not accessible by integration
(updateIssue)`. the drain halts there; nine dispatches across the fleet wait behind one record no
retry can cure. the only cure in practice was a hand delete of the record file (#591).

### now (main)

the same refusal sets that one record aside and the rest deliver, oldest first; a rate limit still
halts. the drain that met the refusal prints github's words once. a clone that reads `get` later
sees only `state: set aside (upstream:access)` and its fix lines — the words are gone.

### after (this route)

`get` adds one line beneath the state: `refusal: GraphQL: Resource not accessible by integration
(updateIssue)`. the record keeps that headline — first line only, echoed command cut, bounded, and
dropped whole if it carries a clock value or a token shape — so the tracked file stays stable and
commit-safe.

### the aha

a refusal costs the one record that earned it, and anyone who reads the queue later sees github's
own reason beside the fix — no rerun, no guess.

## mental model

- a dispatcher would say: *"github said no to one held task; the radio put it to the side, sent the
  rest, and `get` tells me what github said and what to do."*
- analogy: a mail clerk with a stack of letters, one addressed to a bricked-up door. the clerk
  sets it on the return shelf with a note in the recipient's own words, and walks the rest of the
  route. a storm (rate limit) still sends the clerk home.
- terms: the wish says **park**; the code says **set aside** — one state, one word (F2). we keep
  `set aside`. **refusal** names github's answer; **fix** names the move that retries it.

## evaluation

- goals: unwedged backlog ✅ (main) · transient halts ✅ (main) · `get` shows refusal + fix — fix ✅
  (main), refusal text ➕ (this route) · clamp red→green ➕ (red today on the refusal line)
- pros: no new state or verb; one nullable field; the extant fix lines untouched
- cons: a headline dropped on a clock value shows no `refusal:` line; the reader falls back to the

  writes a raw line; the field clears when the reason clears

## groundwork

### external research

github's refusal text is taken from four measured production cases, quoted verbatim in #511,
#551, #591: `GraphQL: Resource not accessible by integration (updateIssue)` and `(repository.issues)`.
no live call was made (a probe would edit a real issue). no new external api.

### internal research

  `upstream:rate-limit`, `upstream:transient`
- classifier: `asRadioUpstreamReason.ts:64-72`; rate-limit phrases are checked before access
  phrases, so a 403 secondary limit halts (`asRadioUpstreamReason.test.ts`, "403 secondary rate

  `.behavior/v2026_10_25.feat-radio-task-queue/.fulcrums/...case=F10-last-fault-as-reason.md`)

## what is awkward?

- a wish built on a defect the base branch already fixed: the honest pr is small, and most of its
  value is evidence, not code
- F3 reverses a recorded fulcrum of #605. it does so with that fulcrum's own reasons kept, but a
  reviewer of #605 may still prefer class-only
- a text sanitize on upstream error lines is brittle by nature; the design fails toward "no line",
  never toward "raw line"
