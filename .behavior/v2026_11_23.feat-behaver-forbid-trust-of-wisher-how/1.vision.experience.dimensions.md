# 1.vision.experience.dimensions

the experience space of a behaver writer who meets a wish that may carry a how. the axes below are
walked in `1.vision.experience.case=_.md`, one row per tuple, every row verdicted.

## .the axes

| # | axis | closed value set | why it varies the experience | why it is orthogonal |
|---|---|---|---|---|
| D1 | actor | `writer` · `reviewer` · `wisher` | the writer authors the yield; the reviewer grades it; the wisher reads it | an actor is a seat; no value of D2–D5 picks who sits in it |
| D2 | what the wish carries | `why-only` · `how` · `how+why` · `port` | each asks a different trust level of the rule | the content is a fact of the wish text, fixed before any stage runs |
| D3 | the writer's move | `restate` (restate in domain terms + verdict) · `copy` (carry the how as spec) · `overcorrect` (drop a verb or a why-backed constraint the wisher named) | `restate` is the rule obeyed; the other two are its two failure modes | the move is a choice; any move can meet any content, at any stage |
| D4 | stage | `vision` · `criteria` · `blueprint` · `execution` | the slip takes a different shape at each: a design, a requirement, a build plan, code or a comment | the stage is where the route is; it implies no content or move |
| D5 | guard variant | `light` · `heavy` | it decides which gate meets a slip: criteria has a guard only when `heavy` | the variant is set once at `init.behavior`; it implies no content, move, or stage |
| D6 | what the review is handed (reviewer only) | `scope.whole` · `scope.starved` · `rules.only` · `rules.companion-only` · `brain.finds` · `brain.fails` | a reviewer can grade only the files and rules its lane is handed, and only when its brain answers | the input is set by the guard template and the review skill, before any yield exists; it implies no content, move, or stage |

### .D6, enumerated — and why it is reviewer only

D6 is the review's own input, surfaced at verification by the suites that prove it
(`initBehaviorDir.laneScope.integration.test.ts`, `review.behavior.integration.test.ts`). its values
split by the two things a lane is handed and the one call it makes:

| value | the review is handed | the experience |
|---|---|---|
| `scope.whole` | the yield and every experience file the lane grades | the verdict covers what the lane claims to read |
| `scope.starved` | the yield alone: bhrain drops a non-yield route file as paperwork when the glob also matches the yield (bhuild#496) | an approved verdict over files the lane never read |
| `rules.only` | each `rule.*.md`, and never a rule's `.reason.md` or `.example=*.md` | the reviewer grades the law, not its argument or its case |
| `rules.companion-only` | a rules dir that holds only a rule's companion | no law to grade |
| `brain.finds` | a brain reply that names a blocker and a nitpick | the caller sees each one listed and counted |
| `brain.fails` | a brain call that exits non-zero | no verdict to read |

the writer and the wisher never meet D6: they see the verdict, not the lane's input. it is walked
once per value, at the reviewer, independent of D2–D5.

### .D2, enumerated — and why the set is closed

the set is closed by **the trust level** the rule assigns. every kind of wish content earns one of
four:

| value | the wish holds | trust the rule assigns |
|---|---|---|
| `why-only` | a purpose and the verbs asked for; no how | full on the why, rough on the verbs |
| `how` | the verbs, plus a how with no domain why: a poc or prior command · a parity target set by a prior tool · a named mechanism, field list, flag set, or storage layout · a done-when phrased by a prior tool | none on the how as spec; rough on the verbs |
| `how+why` | the verbs, plus a how the wisher ties to a domain why ("secrets never leave the keyrack") | the how kept as a constraint, stated with its why |
| `port` | the product **is** a replacement for tool X | X's observable contract is the rough contract; X's internals are a `how` |

`port` is the one value that can wrap another: a replacement of X may also carry a why-backed
constraint ("replace X; never let card numbers leave the host"). D2 takes the product's frame, so
such a wish is `port`; its constraint is graded as a `how+why` within it, by the same rows. no
combined cell is owed: the writer's moves on X's contract and on the constraint are each walked
already, and neither changes the other.

every value carries verbs, so `overcorrect` (drop a verb) can meet every value. the four `how`
sub-kinds share one trust level and one move set, so they are one value; the inventory names a
sub-kind where a demo needs it.

### .D5, reduced

D5 changes the experience only at `criteria` × a slip (`copy` or `overcorrect`). on a `light` route
there is no criteria guard (`getAllTemplatesBySize.ts:38`), so neither the strike test nor the
inverse check runs there. a slip is first met by the next guarded stone,
`3.3.1.blueprint.product.guard.light`, whose `wisher-how` peer lane grades the criteria and blueprint
yields with the wish at refs (F7). at `vision`, both variants carry the same self-review and peer
lane. at `execution`, no gate of this work changes by variant. so D5 adds seven rows: one per D2
value that can be copied (`c.how.copy@light`, `c.hww.copy@light`, `c.port.copy@light`) and one per
D2 value that can be overcorrected (`c.why.overcorrect@light`, `c.how.overcorrect@light`,
`c.hww.overcorrect@light`, `c.port.overcorrect@light`). `restate` gains no row: a gate that passes a
clean yield reads the same whichever stone it sits on.

### .where an axis is degenerate — and why

| actor | degenerate axes | why |
|---|---|---|
| writer | none | the full product is walked |
| reviewer | D3 is what it **reads**; D2 folds into the read | a reviewer grades the writer's move; what the wish carried shows only through that move |
| wisher | D3 = `restate` · D4 = `vision` | the wisher reads a vision; a slip reaches the wisher only via a review the reviewer rows cover |

## .the arithmetic

| actor | free axes | product | rows |
|---|---|---|---|
| writer | D2 (4) × D3 (3) × D4 (4) | 48 | 28 (11 vision + 11 criteria + 3 blueprint + 3 execution) + 7 D5 rows + 1 impossible note |
| reviewer | D3 read (3) × D4 (4) | 12 | 9: `restate` is one read at every stage (1); `copy` and `overcorrect` split by stage (4 + 4) |
| reviewer | D6 (6), apart from D2–D5 | 6 | 6: one row per value |
| wisher | D2 (4), at `restate` × `vision` | 4 | 4 |

the writer reduction, stated:

- `why-only` × `copy` is **impossible** by nature: no how to copy. one note stands for every stage
- `blueprint` × any D2 collapses by move: by then the wish's how+why and port contract are
  criteria, so the plan is graded against one set of requirements whatever the wish carried.
  → 3 rows (`restate`, `copy`, `overcorrect`). the blueprint is where a how is chosen, so `restate`
  here may adopt a poc's mechanism, with a domain reason
- `execution` × any D2 collapses by move: the code or comment is the same artifact whatever the
  wish carried. → 3 rows (`restate`, `copy`, `overcorrect`)
- the rest: vision × D2 × D3 and criteria × D2 × D3, less `why-only × copy` → 11 rows per stage

## .the boundaries a walk can cross

a boundary counts for a row only when the row's own walk visits both sides of it:

- **wish → yield** — the writer turns wish text into a durable artifact. every writer row
- **evidence → spec** — a how is read as evidence, then restated, carried as spec, or discarded
- **yield → review** — a self-review or peer reviewer reads the yield against the rule
- **stage → stage** — a slip made at one stage is carried into the next (vision → criteria, criteria → blueprint)
