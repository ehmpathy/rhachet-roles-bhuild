# 1.vision — fix-envision

> pull experiential demonstration **forward** to the vision stage, so experiential gaps
> surface where they're cheap to fix (at envisioning) instead of where they're expensive
> to discover (at delivery).

---

## the wish, restated

today the vision stone narrates an **implied** experience. it asks "what does a
day-in-the-life look like?" — and the author answers in prose. but nobody ever
*demonstrates* the experience. no concrete walkthrough. no "surfer types X, sees Y".

result: executions walk all the way to the end and reveal big experiential gaps —
gaps that should have been caught at the vision, when they cost a paragraph to fix,
not a rebuild.

the fix: the vision stone should **require concrete experiential demonstrations**:

- one file per demonstrated experience — `1.vision.experience.case=N.$slug.md`
- a catalog that indexes them — `1.vision.experience.case=_.md`
- each demonstration rendered **twice**: as a **narrative** (the felt story) and as a
  **bdd `[tn]` timeline** (the formal given/when/then translation of that story)
- guard **self-reviews and peer-reviews** that grade *experience coverage*: were any key
  experiences from the wish skipped?

### the shared objective: declare the critical paths, exercise the boundaries

the demonstrations are not a random sample of happy stories. their **shared objective is
to declare the critical paths** — and to **exercise as much of the boundary surface as
possible**. three kinds of boundary must be walked:

| boundary | what it is | example demo |
|----------|------------|--------------|
| **positive boundary** | the happy path at its edge — the successful limit, the max-valid input | book the last open slot; the largest valid order |
| **negative boundary** | the rejection path at its edge — the first invalid input, the error limit | book a closed spot; one-over the max; an unbound route |
| **seam** | an interface/handoff between components, where one part's output is another's input | cli → domain op; domain op → external api; vision output → criteria input |

the coverage bar is not "one happy narrative" — it is "the critical positive boundaries, the
critical negative boundaries, and the seams are each demonstrated." a vision that only walks
the sunny middle has left the boundaries — where defects hide — undeclared.

## the outcome world

### before / after

| | before (today) | after (this wish) |
|---|---|---|
| vision output | `1.vision.yield.md` — prose that *narrates* an implied experience | same, **plus** `1.vision.experience.case=N.*.md` demos + a `case=_` catalog |
| experience form | one voice: abstract prose ("users would run the skill and it just works") | two voices per experience: **narrative** (felt) + **bdd `[tn]`** (formal) |
| gap detection | at `5.5.playtest`, *after* execution — via `has-vision-coverage` | at `1.vision`, *before* execution — via a new `has-experience-coverage` review |
| a skipped experience | discovered by a foreman doing byhand QA on finished code | discovered by a reviewer reading the vision, blocking the stone |
| cost to fix a gap | rebuild / rework — the execution already committed to a shape | rewrite a demo paragraph — nothing is built yet |

### a day-in-the-life

**vlad wishes** for a behavior. he writes `0.wish.md` and drives the route.

at the **vision** stone, the clone no longer just writes prose. it enumerates the
distinct **experiences** the wish implies, and for each one writes a `case=N` file that
tells the story twice — once as a narrative a human feels, once as a `[tn]` timeline a
machine could later assert. it lists them all in the `case=_` catalog.

then the **vision guard** runs. a self-review asks: *"walk the wish — is every experience
it implies demonstrated in a case file? which are missing?"* the clone finds it demoed the
happy path but never demoed the **error** experience. it adds `case=3.error-when-unbound`.
a peer-review double-checks and agrees coverage is now complete.

the human approves a vision that already **shows**, not just tells. execution builds
against concrete demonstrations. at `5.5.playtest`, `has-vision-coverage` now has real
experiences to check against — and finds **no surprises**, because the surprises were
caught two stones earlier.

### the "aha"

> the vision stops being a promise and becomes a **demo reel**.
>
> you can no longer write "and then it just works" — you have to show the keystrokes and
> the output. the moment you try, you discover the experiences you were hand-waving past.

## the experiences (testdrive — dogfooded on *this* wish)

to prove the contract, i apply it to itself. below is the `case=_` catalog and two `case=N`
demonstrations of *this* wish's own experiences, in the exact narrative + `[tn]` shape the
new template would mandate. (in execution these become sibling files; embedded here so the
vision itself demonstrates what a vision should now contain.)

### `1.vision.experience.case=_.md` (catalog)

each row is tagged by the **boundary** it exercises (positive / negative / seam), so the
coverage review can confirm the critical-path surface is walked, not just sampled.

| case | slug | boundary | actor | experience | covered? |
|------|------|----------|-------|------------|----------|
| 1 | author-demos-an-experience | positive | clone (vision author) | writes a case file: narrative + `[tn]` | ✓ |
| 2 | review-catches-skipped-experience | negative | clone (self-review) | coverage review blocks a missing experience | ✓ |
| 3 | catalog-indexes-the-cases | seam | clone (vision author) | the `case=_` catalog ↔ the case files stay in sync | ✓ |

> critical paths declared: positive boundary (author demos), negative boundary (review
> blocks a gap), seam (catalog ↔ cases). **each boundary kind is exercised — none skipped.**

### `1.vision.experience.case=1.author-demos-an-experience.md`

**narrative**

the clone is at the vision stone for some wish. it has written the outcome-world prose.
now, instead of stopping, it asks: *"what experiences does this wish imply?"* it names the
first — a surfer books a lesson. it opens `1.vision.experience.case=1.book-a-lesson.md` and
writes the story: the surfer runs `booklesson --surfer kai`, sees a confirmation with the
spot and time, feels certain the slot is held. then it writes the same story as a `[tn]`
timeline, so the experience is both *felt* and *formal*. the gap between "it just works"
and "here is exactly what works" is now impossible to hide.

**bdd `[tn]` timeline**

```
given a surfer "kai" and an open spot "trestles"
  when [t0] kai runs `booklesson --surfer kai`
    then the cli picks the nearest open spot by default
    and  prints "🐢 booked kai at trestles, sat 7am"
  when [t1] kai runs `booklesson --surfer kai` again
    then the same slot is returned (idempotent)
    and  no second booking is created
```

### `1.vision.experience.case=2.review-catches-skipped-experience.md`

**narrative**

the clone thinks it's done — it demoed the happy path. the vision guard fires a self-review:
*"walk every experience the wish implies. for each, is there a case file? which are absent?"*
the clone walks the wish and realizes the wish implied an **error** experience — booking a
closed spot — that it never demonstrated. the review is a **blocker**, so the clone can't
pass. it writes `case=3.error-when-spot-closed` (narrative + `[tn]`), updates the catalog,
and only then does coverage clear. the gap died at the vision, for the price of one file.

**bdd `[tn]` timeline**

```
given a vision.yield with only case=1 (happy path) demonstrated
  and  the wish implies a happy path AND an error path
  when [t0] the vision guard runs `has-experience-coverage` self-review
    then the review enumerates wish-experiences: {book, error-on-closed}
    and  detects case for "book" ✓, no case for "error-on-closed" ✗
    and  reports 1 blocker (an uncovered experience)
  when [t1] the clone adds case=3.error-when-spot-closed + updates catalog
    then re-run reports 0 blockers
    and  the stone may proceed to approval
```

## user experience

### who, and what goal

| actor | goal | usecase |
|-------|------|---------|
| clone (vision author) | show, not tell | declare the critical paths — positive boundaries, negative boundaries, seams; write a `case=N` demo (narrative + `[tn]`) for each; index + tag in `case=_` |
| clone (self-reviewer) | catch gaps early | run `has-experience-coverage`; block if any critical path (positive / negative / seam) lacks a demo |
| peer reviewer (light-enrolled, experience-focused) | second opinion on boundary coverage | independently confirm the boundary surface is exercised — before human approval |
| human wisher | approve with confidence | read demos that *show* the experience at its boundaries, not prose that promises it |

### contract inputs & outputs

this wish's contract is **the vision stone template + its guards**. the change:

**inputs** (unchanged): `0.wish.md`.

**outputs** (added):
- `$BEHAVIOR_DIR_REL/1.vision.experience.case=N.$slug.md` — one per demonstrated experience
- `$BEHAVIOR_DIR_REL/1.vision.experience.case=_.md` — the catalog. NOT merely an index: it is
  the **coverage contract**. it asserts "these are the critical paths the wish implies", tags
  each by boundary kind (positive / negative / seam), and the coverage review grades that
  claim against the wish. so the review is *enumerate-then-grade*: first name every critical
  path the wish implies — its positive boundaries, negative boundaries, and seams — then check
  each has a demo. these are SIBLING files, never inline sections of `1.vision.yield.md`.

**behaver brief** (added): a new `define.experience` brief in the behaver role — path
`src/domain.roles/behaver/briefs/practices/behavior.vision/define.experience.md` (new
`behavior.vision/` practice dir). it is the **canonical definition** the stone, self-review,
and peer review all cite:
- an *experience* is **an actor's lived encounter _with_ a behavior** (POV of the actor)
- one behavior has **many experiences** — different folks encounter it differently
- the experience surface = **actors × boundaries** (positive / negative / seam)
- how it relates to *behavior*: behavior = what the system does; experience = someone who
  lives through it — a relationship, not a synonym

**stone guidance** (added): a `## the experiences` section that directs the author to
enumerate wish-implied experiences and demo each as narrative + `[tn]`. the section cites the
`define.experience` brief for the definition, so the stone stays terse.

**guard reviews** (added, to *both* `light` and `heavy` variants): a self-review
`has-experience-coverage` PLUS a **peer review focused specifically on experience coverage**,
enrolled at the LIGHT level (so both variants carry it — per the wisher, FULCRUM 2 decided).
the self-review *surfaces* an uncovered experience to the human under the `approved?` judge
(`1.vision.guard.light` line 12); the peer review adds an independent coverage check that a
`reviewed?` judge can auto-block on. the peer reviewer's rubric is scoped to one concern —
"are the critical paths the wish implies — its positive boundaries, negative boundaries, and
seams — each demonstrated, and is as much of the boundary surface exercised as possible?" —
not the whole vision.

**review severity** (decided): a **missing critical path** — a positive boundary, negative
boundary, or seam the wish clearly implies but no case demonstrates — is a **BLOCKER**. thin
**thoroughness** — the critical paths are covered, but more edge cases would strengthen the
picture — is a **NITPICK** (flag, do not block). this keeps the bar at "the critical-path
surface is declared" without demanding exhaustive enumeration of every conceivable case.

### the timeline a clone goes through

```
given a bound route at the vision stone
  when [t0] clone reads 0.wish.md
    then it drafts 1.vision.yield.md (outcome world, mental model, ...)
  when [t1] clone reaches the new `## the experiences` section
    then it enumerates the experiences the wish implies
    and  writes 1.vision.experience.case=N.$slug.md for each (narrative + [tn])
    and  writes 1.vision.experience.case=_.md catalog
  when [t2] clone runs `--as passed` → vision guard fires
    then self-review `has-experience-coverage` walks wish vs cases
    and  blocks if any experience is undemonstrated
  when [t3] clone closes gaps, peer-review confirms, human approves
    then execution proceeds against concrete demonstrations
```

## mental model

### how a user describes it to a friend

> "the vision step used to let you *say* 'and then it just works'. now it makes you
> *show the screencast* — type the command, show the output — for every experience the
> wish implies. and a reviewer checks you didn't skip any. so you catch the 'oh, we never
> thought about the error case' moment at the whiteboard, not at the demo."

### analogies

- **storyboard before the shoot** — a film storyboards every key shot before filming;
  you don't discover a missing scene in the editing room. the `case=N` demos are the
  storyboard; execution is the shoot.
- **the demo reel** — the vision becomes a reel of short clips (cases), each shown twice:
  the trailer (narrative) and the shot list (`[tn]`).
- **`5.5.playtest`, shifted left** — the playtest already walks experiences; this is that
  discipline moved to the front, where a gap costs a paragraph, not a rebuild.

### terms — theirs vs ours

| they say | we say |
|----------|--------|
| "walk through it" | experience case |
| "the story" | narrative |
| "the formal steps" / "the test version" | bdd `[tn]` timeline |
| "the list of walkthroughs" | catalog (`case=_`) |
| "did we miss anything?" | experience coverage |

## evaluation

### how well it solves the goal

directly. the wish's root cause is *implied* (never demonstrated) experiences that hide
gaps until delivery. requiring concrete demos + a coverage review at the vision stage
makes the gap **visible at the cheapest possible moment**. it reuses a proven mechanism —
`5.5.playtest`'s `has-vision-coverage` — just shifted left.

### pros

- **cheap gap detection** — an absent experience costs a file, not a rebuild
- **the coverage review is the teeth** — the demo files (R1-R4) give the reviewer a concrete
  artifact to grade, but the *coverage review* (R5-R6) is what actually forces the gap into
  the open. a demo requirement absent a coverage check would let an author demo one path and
  skip the rest. the review is the load-critical half of the fix.
- **dual form serves two downstream uses** — narrative is the human-legible story for review;
  the `[tn]` translation is the machine-shaped form that feeds `2.1.criteria` (bdd) and later
  tests. (two *views* of one story — the wish says "narrative translated" — so `[tn]`
  primarily buys downstream reuse, not a wholly separate gap class.)
- **feeds forward** — the `case=N` files become ready-made scaffolding for `2.1.criteria`
  (bdd), `5.5.playtest`, and acceptance tests. the `[tn]` shape already matches
  `rule.require.given-when-then` and the criteria bdd format.
- **reuses vocab** — `[tn]` timelines, given/when/then, `case=N` / `=_` catalog naming all
  already live in the repo; nothing new to learn

### cons / costs

- **more vision effort** — the vision stage grows heavier. mitigated: the effort is not
  wasted — it's pulled forward from execution/playtest, and feeds those stages.
- **coverage is judgment, not mechanism** — "did you demo every experience?" can't be
  fully automated; it leans on the reviewer walking the wish. same nature as the extant
  `has-vision-coverage` review, so acceptable.
- **risk of ceremony** — a tiny wish shouldn't need 5 case files. the guidance must scale
  down (a one-experience wish gets one case).

### edge cases & pit-of-success

| edge case | how the design keeps the user in the pit |
|-----------|------------------------------------------|
| author demos happy path only | `has-experience-coverage` blocks — it walks the wish and names the missing experience |
| wish implies only one experience | one `case=1` + a one-row catalog is complete; guidance scales down |
| wish has NO user-visible experience (pure internal refactor) | catalog declares "no experiences — internal only"; the coverage review accepts it — mirrors the extant `5.5.playtest` escape ("not in playtest — infrastructure, not behavior") |
| author writes narrative but skips `[tn]` (or vice-versa) | the review requires *both* forms per case |
| catalog drifts from the case files | the coverage review cross-checks catalog rows against the actual case files |
| "experience" vs "behavior" confusion | a case is an *experience* (an actor living a moment), phrased from the actor's POV, not an internal behavior |

## what is awkward?

- **"experience" vs "behavior" — RESOLVED, not a synonym.** an *experience* is not a sibling
  noun to *behavior*; it is **an actor's lived encounter _with_ a behavior**. the behavior is
  what the system does; the experience is someone living through it. because one is the thing
  and the other is the encounter with the thing, there is no synonym drift
  (`rule.forbid.term.addition.synonym` does not fire). the stone carries this one-line
  definition so authors phrase every case from the actor's POV of encountering the behavior.
  crucially, **one behavior has many experiences** — different folks encounter the same
  behavior differently (a surfer, an admin, a ci pipeline each live the booking behavior
  their own way). so the experience surface to exercise is **actors × boundaries**: for each
  actor that matters, walk their critical positive boundaries, negative boundaries, and seams.
- **two forms per case feels like duplication.** writing the same story as narrative *and*
  `[tn]` can read as wet repetition. the justification: they catch *different* gaps (felt
  vs logical). but the guidance must sell that, or authors will resent the second pass.
- **the vision stone is already long.** it has 7 sections; adding an 8th (`## the
  experiences`) plus a heavier guard risks making the vision stage feel like a slog. the
  tradeoff (front-load effort to save rework) is real but uncomfortable — mitigate by
  making the guidance scale down for small wishes.
- **coverage can't be fully mechanized.** "did you demo every experience?" leans on a
  reviewer's judgment walking the wish. it's the same soft-check nature as the extant
  `has-vision-coverage`, but worth naming: this is a *judgment* gate, not a *mechanism*
  gate, and its strength is only as good as the reviewer's read of the wish.
