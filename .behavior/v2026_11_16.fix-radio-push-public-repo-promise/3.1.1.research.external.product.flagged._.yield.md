## topic 1 — how does `runGhCommand` surface a failed `gh repo view`?

**code fact** (`src/access/daos/daoRadioTask/runGhCommand.ts`): `execFileAsync('gh', args, { env, timeout, maxBuffer })`;
on success it returns `stdout.trim()`. on failure it throws, three ways: a call killed by its timeout →
`RadioGhSendTimeoutError` (text names `etimedout`); a 401 → `ConstraintError` (the auth nudge); any
other failure → the original exec error rethrown, with `.stderr` on it.

- [FACT] [1]: "In case of an error (including any error resulting in an exit code other than 0), a rejected promise is returned, with the same `error` object given in the callback, but with two additional properties `stdout` and `stderr`."; "The `error.code` property will be the exit code of the process."; on `timeout`, "the parent process will send the signal identified by the `killSignal` property (the default is `'SIGTERM'`)"
- [FACT] [2]: "If a command fails for any reason, the exit code will be 1"; "If a command requires authentication, the exit code will be 4"
- [FACT] [3]: `gh repo view` will "Output JSON with the specified fields"
- [FACT] [4]: "GitHub uses a `404 Not Found` response instead of a `403 Forbidden` response to avoid confirming the existence of private repositories."
- [OPIN] [5]: "A failure will follow the same execution path as disallowing the operation."
- [OPIN] [6]: "safe defaults should be used"
- [OPIN] [7]: "Base access decisions on permission rather than exclusion."
- **convergence (7 sources):** a failed read always arrives as a throw, of three classes, and its cause cannot be read as "private". ⇒ the visibility read wraps `runGhCommand` in one catch of **every** class and returns `unreadable` with the cause kept for display; it never rethrows, so one fault never halts a drain
- [SUMP] a timeout of the read would, if rethrown, read as `upstream:transient` and halt the whole drain; as `unreadable` it holds one record and the line goes on — the issue's row 5 and the vision's "one held record never blocks the rest" both ask for the latter
- [KHUE] a stdout that parses but lacks a known value (a future enum) — [3] does not promise the set is closed. treat as `unreadable` (fail closed, [5]–[7])

## topic 2 — how does the drain output render a held record's reason and fix?

**code fact**: `asRadioDrainHeldRow.ts` renders `<key> <label> → <owner/name> (<reason>)`, then the fault
detail line (`asRadioFaultDetailLine`), the halt lines, the fix lines from `asRadioQueueFixLines`
(which branch on `record.reason`), and a gate's `lift it (human): …`. `queue get` renders the same
fix lines via `asRadioHeldOutput.ts`; the push output via `asRadioPushOutput.ts` (line 126). a new
reason with no branch in `asRadioQueueFixLines` renders with no fix line.

- [OPIN] [9]: "The Heroku CLI is for humans before machines."; "Input and output should be consistent across commands to allow the user to easily learn how to interact with new commands."; "Human-readable output should be grep-parseable, but not necessarily awk-parseable."
- [OPIN] [8]: "If the command requires input, fail and instruct the user which flag to use instead."
- [OPIN] [10]: "Merely stating the problem is also not enough; offer some potential remedies."
- [FACT] [11]: "the user experience of a warning can have a significant impact on user behavior"
- [FACT] [12]: "For the two attractors that forced the user to interact with the text field containing the change, increasing the level of habituation did not decrease the proportion of participants who responded to the change."
- [FACT] [13]: "habituation—decreased response to repeated stimulation—is a serious threat to the effectiveness of security warnings"
- [OPIN] [9]: a shared output component ensures "that warnings and errors from the API are properly displayed"
- **convergence (5 sources: [8], [9], [10], [11], [12]):** one shape for every held row, a stable greppable reason, and a concrete remedy on each row
- ⇒ the public-repo hold rides the extant row: reasons `public-repo:unpromised` and `public-repo:unreadable` (greppable, parallel to `upstream:*`); a new branch in `asRadioQueueFixLines` names three moves — read the text (`rhx radio.task.queue get`), vouch and send (`rhx radio.task.queue drain --promise task-to-public-repo-is-anonymized`), or drop it (`del --uuid … --why`); the detail line carries `(visibility unreadable — treated as public)` for the unreadable case
- [SUMP] the fix line asks the reader to look at the text first ([12]: interaction with the content resists the fade), then names the promise

## topic 3 — which stub `gh` executables exist across the test suites, and how does each answer?

**code fact**: test suites write a `gh` stub into a temp bin dir and prepend it to `PATH`; each stub logs
its argv to `calls.log`, extracts the repo only from `--repo`, and reads `mode.<owner>_<name>` to pick
an outcome. the stubs on the send path, which every gated send now meets:
`blackbox/role=dispatcher/skill.radio.task.recorder.acceptance.test.ts`,
`src/contract/cli/radioTaskQueue.integration.test.ts`,
`src/domain.operations/radio/record/setRadioTaskRecordsDrained.integration.test.ts`,
`…/setRadioTaskRecordsDrained.sendLimit.integration.test.ts`,
`…/setRadioTaskRecordsDrained.deadline.integration.test.ts`,
`…/setRadioTaskRecordsDrainedByPush.case9.integration.test.ts`. `repo view` takes the repo
positionally, so no stub's `--repo` extract sees it.

- [OPIN] [14]: "Stubs provide canned answers to calls made during the test, usually not responding at all to anything outside what's programmed in for the test."
- [OPIN] [14]: "Fake objects actually have working implementations, but usually take some shortcut which makes them not suitable for production"
- [FACT] [15]: a tool that creates mocks in `$FAKE_BINDIR`; "it's up to you to make sure this directory is in your $PATH"
- [FACT] [16]: the stub of a binary takes `export PATH=tests/stubs:$PATH`
- [OPIN] [17]: "make external-command fakes exact and fail closed"; unknown or mismatched commands must fail the fixture and never fall through to a live executable
- [FACT] [18]: a configurable stand-in for the external CLIs integration tests fake on PATH, which reads its behavior from a JSON config file
- [OPIN] [19]: the repeated stub scaffold (shebang, log line, chmod) moved into a shared factory, since copies drift
- **convergence (5 sources: [14]–[18]):** a stub first on PATH, with canned answers, is standard; an unknown call must fail closed
- ⇒ each send-path stub gains one branch before its mode checks: `repo view` → `{"visibility":"PRIVATE"}`, overridable per repo by a `visibility.<owner>_<name>` file; extant journeys stay green and new tests set PUBLIC / INTERNAL / a failure per repo
- [FACT] the fail-closed property holds by construction: a stub with no `repo view` branch makes the read fail, the read returns `unreadable`, the gate holds, the test goes red — never a silent send ([17])
- [OPIN] [19] suggests one shared stub factory; this repo's six copies drift today. a shared factory is a fix that ripples across six suites — a candidate dream, not this wish's scope

## topic 4 — which real-github tests push text into the public demo repo?

**code fact**: `ehmpathy/rhachet-roles-bhuild-demo` is public (`gh repo view --json visibility` →
`PUBLIC`). `GITHUB_DEMO_REPO` (`blackbox/.test/infra/constants.ts`) is used by
`blackbox/role=dispatcher/skill.radio.task.push.via-gh-issues.acceptance.test.ts`; the integration
tests `src/access/daos/daoRadioTask/daoRadioTaskViaGhIssues.integration.test.ts` (dao level, below the
gate) and `src/domain.operations/radio/record/setRadioTaskRecordsDrainedByPush.integration.test.ts`
(case7, a 401 under a bad token) also target it.

- [OPIN] [20]: contract tests "check that all the calls against your test doubles return the same results as a call to the external service would."; doubles raise "the question of whether the double is indeed an accurate representation of the external service"
- [OPIN] [21]: "If there's no way to run a third-party service locally you should opt for running a dedicated test instance and point at this test instance when running your integration tests."
- [OPIN] [21]: "Avoid integrating with the real production system in your automated tests."
- [FACT] [3]: the read takes `--json visibility`; [2]: failures exit 1 or 4
- [FACT] [22]: "GH Archive is a project to record the public GitHub timeline, archive it, and make it easily accessible for further analysis."
- [OPIN] [23]: "You should not ignore repeated `4xx` and `5xx` error codes."
- [OPIN] [14]: a stub answers only what it was programmed for
- **convergence (4 sources: [14], [20], [21], [3]):** the demo repo is the dedicated test instance; one real `gh repo view` against it is the contract test that keeps the stubs' PUBLIC / PRIVATE answers honest
- ⇒ the gh-issues push journeys owe `--promise task-to-public-repo-is-anonymized` (their text is test fixture, anonymized by construction). the dao integration test sits below the gate and owes none. case7 (401) must carry a promise on its record, so it skips the visibility read and still reaches the 401 it asserts
- [FACT] every issue these tests create is public and archived within the hour ([22]); their titles and bodies must hold only sandpine demo text — already the repo rule (`rule.forbid.private-business-in-published-roles`)
- [KHUE] the integration test of the visibility read itself: the demo repo answers PUBLIC for real; a private answer needs a private repo the test token can read. the stub covers private / internal / a failure ([20]: the real call proves the shape, the stub proves the branches)

## .conflicts

- **[14] vs [17]:** [14] says a stub answers "usually not responding at all" outside its program; [17] says an unknown call must fail loud. here a silent non-answer from `gh` is an exit 1, which the read turns into `unreadable` — a loud hold, so both hold
- **[21] vs topic 4:** [21] says avoid the real production system; the demo repo is real github, but a dedicated test instance, which [21] endorses
- **[13] vs [9]:** [13] warns a repeated, unchanged warning fades; [9] asks for consistent output across commands. the held row keeps one shape ([9]); the fade is fought by rarity and by a fix line that points at the text ([12])

- a new `asRadioQueueFixLines` branch for `public-repo:*` reasons; no new row renderer
- six send-path stubs gain a `repo view` branch (default PRIVATE, per-repo override)
- the demo-repo push journeys carry `--promise`; case7 carries a promise on its record
