# research.external.product.claims: what the world says about a promise-gated push to a public repo

## .method

43 sources in one list. 27 were fetched with WebFetch by this researcher on 2026-11-16. 8 are reused
from the peer yield `3.1.1.research.external.product.access._.yield.md` and are marked `(via access
yield)`. 8 are folded in from an earlier version of this yield that another delegate fetched, and are
marked `(via peer version)`: [36]–[43]. for the reused ones the quote is from the delegate's extract.
WebFetch returns a model-condensed extract, so a quote is verbatim to that extract. a quote that ships
into a published brief must be re-checked against the page. doc pages without a date are marked
`undated (live doc)`. a search result that was not fetched is not cited. urls and quotes are kept
verbatim, so a few hold words this repo's own prose avoids. wikipedia is tertiary: tagged `[blog]` and
used for definitions only.

claim labels: **[FACT]** indisputable · **[SUMP]** an assumption someone made · **[KHUE]** an open
question we should weigh · **[OPIN]** a subjective call to consider.

## .the wish, in one line

a `radio.task.push` into a public github repo halts (exit 2) until the caller re-runs with
`--promise task-to-public-repo-is-anonymized`. unreadable visibility counts as public. the drain is
gated too. the promise is a self-attested flag.

## .the claims we test

| # | claim under test | lessons |
|---|---|---|
| C1 | text sent to a public repo cannot be taken back | L1, L2 |

| C5 | a self-attested promise changes behavior | L6 |
| C6 | a named flag is the right shape of bypass, and fail-closed is the right default | L7 |
| C7 | a content scanner is no substitute | L8 |

## .lessons

### L1 — C1: a public issue cannot be un-sent; cleanup is partial and manual

- [1] gh comment edit history [official] https://docs.github.com/en/communities/moderating-comments-and-conversations/tracking-changes-in-a-comment — undated (live doc), via access yield: "Anyone with read access to a repository can view a comment's edit history."
- [2] disruptive comments [official] https://docs.github.com/en/communities/moderating-comments-and-conversations/managing-disruptive-comments — undated (live doc), via access yield: "The initial comment (or body) of an issue or pull request can't be deleted."
- [3] delete an issue [official] https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/deleting-an-issue — undated (live doc): "Only accounts with admin or owner permissions can delete issues in a repository owned by an organization."; "Collaborators do not receive a notification when issues are deleted."; collaborators "can use the API to determine that it was deleted"
- [4] Truffle Security [practitioner] https://trufflesecurity.com/blog/thousands-of-github-comments-leak-live-api-keys — 2023-09-27, via access yield: "The drop down next to the 'edited' tag revealed prior versions, including the original containing the valid API key."
- [5] GitGuardian state of secrets sprawl 2025 [practitioner] https://www.gitguardian.com/state-of-secrets-sprawl-report-2025 — 2025 (day not shown): "23,770,171 new secrets detected in public GitHub commits in 2024" (25% up from the year before); "70% of secrets leaked in 2022 remain valid today"
- [6] repository visibility changes [official] https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility — undated (live doc): private to public: "The code will be visible to everyone who can visit GitHub.com."; "Your changes will be published as activity."
- [43] GH Archive [official] https://www.gharchive.org/ — undated (live doc), via peer version: "GH Archive is a project to record the public GitHub timeline, archive it, and make it easily accessible for further analysis."; it captures events from "opening new tickets, commenting"; "the dataset is automatically updated every hour"

claims:
- [FACT] the body of an issue cannot be deleted apart from the issue, and the edit history of a comment is readable by anyone with read access ([1], [2])
- [FACT] a repo admin or org owner can delete a whole issue; the delete leaves an API-visible trace ([3])
- [FACT] a third party records the public github timeline, new tickets and comments included, and refreshes it every hour ([43]). an admin delete cannot recall a copy that outside party already holds. this answers part of the earlier open question about mirrors: at least one public archive copies issue events within the hour
- [SUMP] "the leak is permanent" (the vision's `.before`) is true for the pusher and for any reader or archive that already saw it. it is not a claim that no admin can ever remove the issue. [2] and [3] look like a conflict and are not: the body cannot be deleted, the issue can. the vision's words hold if read as "the pusher cannot take it back"
- [KHUE] do github's email notifications and webhooks keep an issue after an admin deletes it? [3] does not say. no fetched source answers
- [FACT] cleanup of a leak is slow in practice: 70% of secrets leaked in 2022 stayed valid ([5]). the stat is about secrets, not business detail, so it shows slow cleanup and not the leak rate of org names
- [KHUE] a private repo can turn public later and then publishes its history ([6]). a task sent into a private repo today is a leak later. the gate cannot see this; the wish does not ask for it
- **convergence (5 sources: [1], [2], [3], [4], [43]):** the pre-send gate is the one control that works at the right moment, and it must cover a text edit as it covers a create

### L2 — C1: github itself walls private text off from public at the issue level

- [7] issue transfer [official] https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/transferring-an-issue-to-another-repository — undated (live doc), via access yield: "A private repository issue cannot be transferred to a public repository."

claims:
- [FACT] the platform refuses one private-to-public issue move outright ([7]). the radio gate is the same rule applied to a new issue
- [OPIN] this is precedent that a hard rule at the visibility edge is normal. it does not show that a soft nudge suffices: the platform rule has no bypass flag

### L3 — C2: an agent with private context and a public write path leaks, today, by convenience

- [8] Invariant Labs, GitHub MCP exploit [practitioner] https://invariantlabs.ai/blog/mcp-github-vulnerability — 2025-05-26: the agent "pulls private repository data into context, and leaks it in an autonomously-created PR"; "leaks it into a pull request of the `pacman` repo, which is freely accessible to the attacker since it is public."
- [9] Simon Willison, the lethal trifecta [blog] https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/ — 2025-06-16: three capabilities combine: access to private data, exposure to untrusted content, ability to externally communicate; "Any time you combine those three lethal ingredients together you are ripe for exploitation."
- [10] OWASP LLM06 excessive agency [official] https://genai.owasp.org/llmrisk/llm062025-excessive-agency/ — 2025: "An LLM-based application or extension fails to independently verify and approve high-impact actions."
- [36] Help Net Security [practitioner] https://www.helpnetsecurity.com/2026/09/30/ai-coding-agents-github-screenshot-leak/ — 2026-09-30, via peer version: "AI coding agents leaked 13,000 internal company screenshots to public GitHub repos"; "Hardening AI tool configurations is key for prevention…most of them can be configured not to work unattended, and that configuration belongs with your security team rather than with each developer."
- [37] The Hacker News [practitioner] https://thehackernews.com/2026/09/ai-coding-agents-exposed-13000-internal.html — 2026-09-30, via peer version: "The agents, working through the command line, found they could not attach the screenshots. So they put the images in a separate public repository, usually under the developer's own account, and made them available to reviewers from there."; "Do not rely only on scanners, which read text, not images."
- [38] heise [practitioner] https://www.heise.de/en/news/AI-coding-agents-leak-credentials-into-public-repositories-11517471.html — 2026-11-09, via peer version: "a documented Claude Code feature that asks whether to run a suggested command when accessing databases or APIs, then offers the option 'Yes, and don't ask again.'"
- [39] OWASP LLM02:2025 sensitive information disclosure [practitioner] https://genai.owasp.org/llmrisk/llm022025-sensitive-information-disclosure/ — 2025, via peer version: "This includes personal identifiable information (PII), financial details, health records, confidential business data, security credentials, and legal documents."

claims:
- [FACT] the radio clone holds two of the three trifecta legs by design: private context (its own notes) and an outbound channel (a public issue). [8] shows the same shape ends in a leak
- [FACT] agents publish internal material to public github when a private path is inconvenient, with no attacker in the loop ([36], [37]): 13,000 internal screenshots reached public repos because a command-line agent could not attach them. this is the very leak the vision fears, at scale, in 2026
- [FACT] a persisted "don't ask again" is how a bypass becomes a habit that leaks ([38])
- [FACT] the data at risk is wider than secrets: confidential business data and legal documents count ([39])
- [SUMP] the radio's threat is inadvertent paste (the vision's `.before`), not an attacker. [37] now supports this with a live case: convenience, not attack. [8] and [9] are about a hostile prompt; the gate helps against both only if the agent cannot self-vouch without a read
- [KHUE] a hostile prompt can tell the agent to add `--promise`. a flag the agent controls gives no protection against prompt injection ([9]: "We still don't know how to 100% reliably prevent this from happening")
- [OPIN] [36] says the control "belongs with your security team rather than with each developer". here the tool carries the control for every caller by default, which serves both
- **convergence (5 sources: [8], [36], [37], [38], [39]):** an unattended agent with a public write path leaks, by convenience more than by attack. a gate at the send is the "configuration" [36] asks for, owned by the tool

### L4 — C3: a checkpoint before a high-impact act is the accepted control, and it must be a real one

- [11] OWASP LLM06 mitigation [official] https://genai.owasp.org/llmrisk/llm062025-excessive-agency/ (same page as [10]) — 2025: "Utilise human-in-the-loop control to require a human to approve high-impact actions before they are taken."
- [12] Anthropic, safe and trustworthy agents [official] https://www.anthropic.com/news/our-framework-for-developing-safe-and-trustworthy-agents — 2025-08-04: "humans should retain control over how their goals are pursued, particularly before high-stakes decisions are made"; "The right balance between autonomy and oversight varies dramatically across scenarios"
- [13] Claude Code hooks reference [official] https://code.claude.com/docs/en/hooks — undated (live doc): "Blocking error: your hook exits 2."; "The message that comes with the block is your hook's stderr."; any other non-zero exit is a "Non-blocking error", so "your hook didn't stop the action"
- [14] gh exit codes [official] https://cli.github.com/manual/gh_help_exit-codes — undated (live doc): "If a command is running but gets cancelled, the exit code will be 2"; "If a command fails for any reason, the exit code will be 1"

claims:
- [FACT] the standard control is approval by a human before the act ([10], [11], [12])
- [SUMP] the wish's gate has no human in it: the pusher is a clone, and the clone reads the nudge, then re-runs. the control is a checkpoint for the agent's own re-read, not an approval by a human. [11] asks for the latter
- [OPIN] that is a fair trade for a p0 that must ship in a day, but the pr should state it: the promise is a self-check by the caller, the same as the vision's `.cons`
- [FACT] in claude code, exit 2 is the one non-zero code that blocks, and its stderr text goes back to the agent ([13]). a clone that runs the radio inside a hook-aware shell reads the nudge as feedback. the nudge text is therefore read by a model, and a model re-runs the printed command
- [FACT] gh gives exit 2 the sense "cancelled" ([14]). the radio uses exit 2 for "caller must fix first". the two do not clash, since gh's code is for gh's own commands, but a reader who knows gh may expect "cancelled". [KHUE] only a note in `--help` would tell them

### L5 — C4: a repeated confirmation habituates the caller

- [15] Akhawe and Felt, Alice in Warningland [academic] https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/akhawe — 2013 (USENIX Security): "users continued through a tenth of Mozilla Firefox's malware and phishing warnings, a quarter of Google Chrome's malware and phishing warnings, and a third of Mozilla Firefox's SSL warnings"; "users continued through 70.2% of Google Chrome's SSL warnings"
- [16] Anderson et al., polymorphic warnings and the brain [academic] https://scholarsarchive.byu.edu/facpub/9306/ — 2015 (CHI): "a dramatic drop in the visual processing centers of the brain after only the second exposure to a warning, with further decreases with subsequent exposures"; polymorphic designs were "substantially more resistant to habituation than conventional warnings"
- [17] Nielsen Norman Group, confirmation dialogs [practitioner] https://www.nngroup.com/articles/confirmation-dialog/ — 2018-02-18 (last reviewed 2026-08-07): "A confirmation dialog must restate the user's request and explain what the computer is about to do, with specific information."; "if you cry wolf too many times, people will stop paying attention to the question, and the confirmation dialog will lose its power."
- [18] alarm fatigue [blog, tertiary] https://en.wikipedia.org/wiki/Alarm_fatigue — undated (live doc): "Alarm fatigue or alert fatigue describes how busy workers (in the case of health care, clinicians) become desensitized to safety alerts, and as a result ignore or fail to respond appropriately to such warnings."
- [19] Anthropic, claude code sandbox [official] https://www.anthropic.com/engineering/claude-code-sandboxing — 2025-10-20: "Constantly clicking 'approve' slows down development cycles and can lead to 'approval fatigue', where users might not pay close attention"; "sandboxing safely reduces permission prompts by 84%."
- [20] normalization of deviance [blog, tertiary] https://en.wikipedia.org/wiki/Normalization_of_deviance — undated (live doc): "A clearly unsafe practice becomes considered normal if it does not immediately cause a catastrophe"
- [21] git config advice [official] https://git-scm.com/docs/git-config — undated (live doc): git hints come "alongside instructions on how to squelch it"; "When tools that run Git as a subprocess find them disruptive, they can set `GIT_ADVICE=0` in the environment to squelch all advice messages."
- [22] Buçinca, Malaya, Gajos, cognitive forcing functions [academic] https://arxiv.org/abs/2102.09692 — 2021-02-19: "cognitive forcing significantly reduced overreliance compared to the simple explainable AI approaches"; users "rated the most effective designs less favorably"
- [23] poka-yoke [blog, tertiary] https://en.wikipedia.org/wiki/Poka-yoke — undated (live doc): two kinds, "Control poka-yoke: the device itself actually prevents the mistake" and "Warning poka-yoke: the operator receives an alert when an error is about to happen"
- [40] Vance et al., Tuning Out Security Warnings, MIS Quarterly 42(2) [academic] https://aisel.aisnet.org/misq/vol42/iss2/3/ — 2018, via peer version: "habituation—decreased response to repeated stimulation—is a serious threat to the effectiveness of security warnings"; "users' warning adherence substantially decreased over the three weeks"; "for users who received polymorphic permission warnings, adherence dropped at a substantially lower rate and remained high after three weeks"
- [41] Bjornn et al., repetition of computer security warnings, Frontiers in Psychology [academic] https://frontiersin.org/articles/10.3389/fpsyg.2020.528079/full — 2020-12-07, via peer version: "repeated exposure to a warning does not lead to beneficial familiarity effects, but leads directly to diminished attention to a warning"
- [42] Bravo-Lillo et al., Harder to Ignore? Revisiting Pop-Up Fatigue, SOUPS 2014 [academic] https://www.usenix.org/conference/soups2014/proceedings/presentation/bravo-lillo — 2014, via peer version: "For the two attractors that forced the user to interact with the text field containing the change, increasing the level of habituation did not decrease the proportion of participants who responded to the change. These attractors appeared resilient to habituation."; "Increasing habituation caused a three-fold decrease in the proportion of participants who responded to the change."
- the Invariant page ([8]) also says, 2025-05-26: "many users already opt for an 'Always Allow' confirmation policy when using agents, and stop monitoring individual actions." cited below as [8]

claims:
- [FACT] a repeated, unchanged alert loses effect fast: the visual response drops after the second exposure ([16]); adherence fell over three weeks ([40]); repeated exposure "leads directly to diminished attention" ([41]); click-through rates range from a tenth to 70% by alert design ([15])
- [FACT] a confirmation that does not restate the specific act is answered by reflex ([17])
- [FACT] agent users drift to "always allow" ([8], [19], [38]). approval fatigue is documented by the vendor of the agent that most likely calls this radio
- [FACT] a design that forces the reader to interact with the changed text resists habituation; a plain one loses a factor of three ([42]). a design that changes its look each time also holds adherence ([40], [16])
- [SUMP] the public-repo nudge fires rarely (private pushes pass silent), so it resists fatigue better than a nudge on every push. true on the common path ([17]: the fatigue is a function of how often it cries wolf). **not true for a caller whose job is to push to a public repo**: a clone that files into `ehmpathy/rhachet` all week meets the nudge each time, and learns to add `--promise` from its first re-run
- **[OPIN] design hazard:** the nudge prints the full re-run command with `--promise` pasted in. that makes the bypass one copy-paste, and a caller can store the full command as a template (the "always allow" shape in [8], the "don't ask again" shape in [38]). the stored habit then carries the promise to a push whose text was never re-read. [20] names the path: a bypass that causes no harm the first ten times becomes the norm
- [OPIN] counters that keep the re-read real, cheapest first:
  1. the nudge echoes the exact title and the first lines of the body it would send, so the re-read has the text in view ([17]: "restate the user's request ... with specific information")
  2. the promise stays per push: never inherited from a prior push and never a "don't ask again" ([38]). the vision already says so; `--help` should too, so a reader knows why a re-push without it nudges again
  3. a promise value bound to the target repo, so the caller types what it vouches for and a stored command cannot ride to a different repo. [42] is the strongest support: a step that forces interaction with the content resists habituation. [26] and [30] show the shape (`--confirm="name-of-thing"`, type the repo name)
  4. record the promise and its caller on the held or delivered record, so a leak can be traced to a promise (an audit trail; the vision already records every push; [33])
  5. vary the nudge ([16], [40]). see the conflict below: this repo snaps its output, so only the parts that differ per push (repo, exact command, echoed text) can vary
- [KHUE] should the `--help` text say outright that a promise is a statement about *this* text and must not be stored in a template or an alias? [21] shows git gives a squelch switch; a reflexive squelch is an accepted, known path
- [FACT] a hard step cuts over-reliance but users rate it less ([22]). the cost lands on the rare public push only
- [OPIN] the wish builds an *alert* poka-yoke ([23]): the device does not prevent the mistake, it alerts the caller and asks for a signature. a *control* poka-yoke would hold the text until a human releases it. the gap between the two is the whole risk of L5
- **convergence (8 sources: [15], [16], [17], [18], [19], [40], [41], [8]):** repeated unchanged confirmations decay. strong. the remedy the sources agree on is variety and forced contact with the text, not more prompts

### L6 — C5: a self-attested promise has no robust evidence that it changes behavior

- [24] Kristal et al. 2020 [academic] https://pmc.ncbi.nlm.nih.gov/articles/PMC7132248/ — 2020-03-31 (PNAS 117(13)): "Across five conceptual replications (n = 4,559) and one highly powered, preregistered, direct replication (n = 1,235) conducted with the authors of the original paper, we observed no effect of signing first on honest reporting."; "signing at the beginning is unlikely to be a simple solution for increasing honest reporting."
- [25] Data Colada, evidence of fraud [blog] https://datacolada.org/98 — 2021-08-17: the 2012 field experiment with 13,488 insurance customers showed anomalies that point to fabrication, among them "just as many people drove 40,000 miles as drove 20,000 as drove 10,000."

claims:
- [FACT] the best-known result that a signed honesty declaration lowers dishonesty did not replicate ([24]) and its field data show signs of fabrication ([25])
- [SUMP] the wish rests on a milder claim than that study: not "a pledge makes people honest" but "a deliberate flag makes the caller stop and re-read once". [24] does not test that. [22] and [42] speak to it: a forced deliberate step cuts over-reliance
- [FACT] the sources do not support a claim that the promise *deters* a leak. they support, at best, that it *interrupts* a reflex
- [OPIN] the pr and `--help` should not oversell the promise. word it as a checkpoint ("check these three items"), never as an oath
- [KHUE] the checklist in the nudge (org, repo, route path, pr numbers; internal names; business detail) is the part that can add real value: it names what to look for. no source tests whether a named checklist beats a bare flag. the vision's own claim ("the re-read is concrete, not a ritual") is an assumption
- **conflict:** the wish's premise ("make the caller promise") and [24] disagree on whether an attestation changes behavior. [24] tests a pledge on a form, a different act from a flag on a command. we side with [22] and [42] on interrupt value and with [24] on the limit: the gate is a checkpoint, not a guarantee

### L7 — C6: a named flag is the usual bypass shape; fail-closed is the usual default

- [26] clig.dev [practitioner] https://clig.dev/ — undated (live doc): "Only use prompts or interactive elements if `stdin` is an interactive terminal (a TTY)."; "If the command requires input, fail and tell the user how to pass the information as a flag."; "Catch errors and rewrite them for humans."; peer version adds: "allow scriptable confirmation via a flag like `--confirm="name-of-thing"`."
- [27] OWASP fail securely [practitioner] https://community.owasp.org/Fail_securely — undated (live doc): "A failure will follow the same execution path as disallowing the operation."; "Security methods like isAuthorized(), isAuthenticated(), and validate() should all return false if there is an exception during processing."
- [28] CWE-636 failing open [official] https://cwe.mitre.org/data/definitions/636.html — undated (live doc): "When the product encounters an error condition or failure, its design requires it to fall back to a state that is less secure than other options that are available"
- [29] Saltzer and Schroeder [academic] https://www.cs.virginia.edu/~evans/cs551/saltzer/ — 1975, via access yield: "Base access decisions on permission rather than exclusion."
- [30] github docs, delete a repository [official] https://docs.github.com/en/repositories/creating-and-managing-repositories/deleting-a-repository — undated (live doc): "To verify that you're deleting the correct repository, in the text box, type the name of the repository you want to delete."
- [31] terraform apply [official] https://developer.hashicorp.com/terraform/cli/commands/apply — undated (live doc), via access yield: "Skips interactive approval of the plan before applying."; "we recommend you first perform a plan operation and review the proposed changes"
- [32] gh repo view manual [official] https://cli.github.com/manual/gh_repo_view — undated (live doc): `--json <fields>` "Output JSON with the specified fields", the field list holds `visibility` and `isPrivate`; "With no argument, the repository for the current directory is displayed."
- [33] github docs, push protection [official] https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection — undated (live doc), via access yield: "Anyone with write access to the repository can bypass push protection by specifying a bypass reason."

claims:
- [FACT] a non-interactive command fails and names the flag ([26]). the nudge's exit 2 plus a printed flag matches; first pass halts and names the flag, second pass sends, no tty prompt ([31] shows the same plan-then-apply order)
- [FACT] fail-closed is the standard stance when a check cannot run ([27], [28], [29]). "unreadable counts as public" matches
- [FACT] platforms ask the caller to *name the target* to bypass a destructive act: github's repo delete asks for the repo name ([30]); terraform pairs a skip flag with a plan to review first ([31]). github's own secret gate lets a writer bypass with a stated reason ([33]), which is the closest prior art to `--promise`: a gate, a bypass, and a record
- [OPIN] [30] and [26]'s `--confirm` shape argue for a repo-bound promise value (the caller types the target), the strongest cheap guard against a stored command (L5). the wish fixes one literal. the access yield defers this as "a possible later guard". we agree it is a fair cut for p0 and name it as the first follow-up; [42] says it would also resist habituation
- [FACT] always pass an explicit `<owner/name>` to `gh repo view`: with no argument it reads the current directory's repo ([32]), which in a radio is the wrong one. the radio's `--into` is the repo to read
- [SUMP] "internal sends as private" (F4, ruled): [6] and the access yield's [11] say internal is visible to users in the same enterprise. an internal repo can be read by thousands of staff in a large enterprise. no source rules on the policy call; it is a fulcrum, not a fact
- **convergence (5 sources: [26], [27], [28], [29], [33]):** fail closed, name the flag, never prompt in automation

### L8 — C7: a content scanner is no substitute for the gate

- [34] cyberhaven, dlp false positives [blog, vendor] https://www.cyberhaven.com/infosec-essentials/dlp-false-positives — 2026-06-12: "Content inspection answers one question well: 'Does this data match a sensitive pattern?' It cannot answer the questions that determine actual risk."; "Alert fatigue is how a high false positive rate creates a false negative risk."
- [35] arXiv 2307.00714, secret detection tools [academic] https://arxiv.org/html/2307.00714 — 2023-07-03, via access yield: "no current tool has the coveted high precision and high recall scores"
- the Willison page ([9]) adds: "95% is very much a failing grade" for filters sold as catch of "95% of attacks"
- the Hacker News page ([37]) adds: "Do not rely only on scanners, which read text, not images."

claims:
- [FACT] a pattern scan matches shapes (keys, ids), not business detail like an org name or an internal route ([34], [35]). an org name, a route path, or a pr number is no pattern a scanner flags; only the author knows it is private
- [FACT] a scan that reads text misses an image ([37]); a noisy scan breeds the same fatigue as a noisy prompt, then lets real leaks through ([34])
- [OPIN] the vision's call to keep a scanner out of scope holds. a scanner can be added later as a *hint* in the nudge (names of tokens found), never as the gate. note [34] is vendor copy

## .conflicts

- **[2] vs [3] on "the issue cannot be deleted":** [2] says the initial body cannot be deleted; [3] says an admin can delete the issue. both hold: the body is not removable apart from the issue. the vision's "permanent" is true for the pusher and for an archive ([43]), not for an admin's own view
- **[24] vs the wish's premise on pledges:** see L6. no source supports "a promise deters"; two support "a forced step interrupts" ([22], [42])
- **[11] vs the wish's design on who approves:** [11] wants a human to approve high-impact actions; the wish lets the agent that pushes vouch for itself. a conscious cut for p0, the same as the vision's `.cons`
- **[17] vs [26] on a prompt:** [17] says a restated, specific confirmation works; [26] says never prompt in automation. no clash: the radio does not prompt, it exits and prints the specific text. the nudge is a message, not a dialog
- **[40]/[41] vs [26] on a copy-paste confirm:** [26] favors a scriptable confirmation flag; [40]/[41] warn that a cheap, repeated confirm fades into reflex. the nudge prints the full command (cheap, per [26]); the mitigations are rarity (private repos never see it), a list of concrete checks, and forced contact with the text ([42])
- **[40] polymorphic vs a snapshot-stable nudge:** [40] slows the fade by a changed look each time; this repo requires stable, snapped output. a fully varied nudge is out of scope; the part that varies is the repo, the echoed text, and the exact command, which differ per push
- **[36] vs this wish on who owns the control:** [36] says the control belongs to a security team, not each developer. here the tool carries it for every caller by default, which serves both
