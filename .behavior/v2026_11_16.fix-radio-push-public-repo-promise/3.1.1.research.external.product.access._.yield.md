## .the remote we access

one remote, read once per gated send: the github repository's visibility, via the `gh` cli the
radio already shells to (`runGhCommand`, `execFile('gh', args)`).

| contract | how | what it returns |
|---|---|---|
| `gh repo view <owner/name> --json visibility` | argv, under the record's own `GH_TOKEN` (robot) or the gh session (human) | `{"visibility":"PUBLIC"\|"PRIVATE"\|"INTERNAL"}`, exit 0; exit 1 on any failure (exit 4 when auth is required) |

## .lessons

### L1 — the read path is `gh repo view --json visibility`, and visibility has three values
- [1] gh repo view [official] https://cli.github.com/manual/gh_repo_view — undated (live doc): "Output JSON with the specified fields"; the field list includes `visibility`, `isPrivate`
- [2] gh repo list [official] https://cli.github.com/manual/gh_repo_list — undated (live doc): "Filter by repository visibility: {public|private|internal}"
- [8] gh help: json output [official] https://cli.github.com/manual/gh_help_formatting — undated (live doc): `--json` takes "a comma separated list of fields to fetch."
- [11] GraphQL RepositoryVisibility [official] https://docs.github.com/en/graphql/reference/repos — undated (live doc): INTERNAL "visible only to users in the same enterprise." PRIVATE "visible only to those with explicit access." PUBLIC "visible to everyone."
- [12] about repositories [official] https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories — undated (live doc): "Public repositories are accessible to everyone on the internet."
- **convergence (5 sources):** the value set is closed at three
- **take:** parse the json field, never the human output. allow without a promise only on exactly `PRIVATE` or `INTERNAL` (F4); any other value — PUBLIC, an unknown future value, an absent or empty field — gates

### L2 — gh collapses failures to exit 1; the wrapper must classify
- [4] gh help exit-codes [official] https://cli.github.com/manual/gh_help_exit-codes — undated (live doc): "If a command fails for any reason, the exit code will be 1"; "If a command requires authentication, the exit code will be 4"
- [5] gh auth status [official] https://cli.github.com/manual/gh_auth_status — undated (live doc): "The command returns exit code 1 if authentication issues exist on any host"
- **take:** every failure of the read maps to `unreadable`; keep gh's stderr as the cause, for display

### L3 — a failed read is ambiguous: private, absent, and no-access look alike
- [10] REST: get a repository [official] https://docs.github.com/en/rest/repos/repos#get-a-repository — undated (live doc): errors "404: Resource not found", "403: Forbidden", "301: Moved permanently"; schema `visibility: string`, `private: required, boolean`
- [13] fine-grained PAT permissions [official] https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens — undated (live doc): `GET /repos/{owner}/{repo} | read | PAT`
- [14] personal access tokens [official] https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens — undated (live doc): "Tokens always include read-only access to all public repositories on GitHub."
- [15] scopes for OAuth apps [official] https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps — undated (live doc): `public_repo`: "Limits access to public repositories."
- [16] REST API trouble guide [official] https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api — undated (live doc): "GitHub uses a `404 Not Found` response instead of a `403 Forbidden` response to avoid confirming the existence of private repositories."
- **convergence (5 sources):** a read of PUBLIC is reliable; a failed read cannot tell private from absent from no-access. ⇒ unreadable gates, as the issue's row 5 says
- **take:** a token that can read the repo's issues can read its metadata ([13]), so a failure on a repo the radio can write to is rare — but when it occurs it must not read as private

### L4 — automation is token-based and prompt-free; the promise is a flag, never a prompt
- [3] gh help environment [official] https://cli.github.com/manual/gh_help_environment — undated (live doc): "GH_TOKEN, GITHUB_TOKEN (in order of precedence): an authentication token…"; "GH_PROMPT_DISABLED: set to any value to disable interactive prompting in the terminal."
- [7] gh issue create [official] https://cli.github.com/manual/gh_issue_create — undated (live doc): "Supply a title. Will prompt for one otherwise"
- [29] clig.dev [practitioner] https://clig.dev/ — undated (live doc): "Only prompt if `stdin` is an interactive terminal (TTY)."; "If the command requires input, fail and instruct the user which flag to use instead."
- **convergence (3 sources):** no prompt in automation; fail and name the flag
- **take:** the nudge exits 2 and prints the exact flag; it never waits on stdin

### L5 — the send surface is create and edit, and text can arrive by stdin or file
- [6] gh issue edit [official] https://cli.github.com/manual/gh_issue_edit — undated (live doc): `--body-file`: "Read body text from file (use "-" to read from standard input)"
- **take:** the gate keys on the record's text fields, which hold the text however it arrived (`--description @stdin` too)

### L6 — an edit does not take text back: history is public, the issue body cannot be deleted
- [18] comment edit history [official] https://docs.github.com/en/communities/moderating-comments-and-conversations/tracking-changes-in-a-comment — undated (live doc): "Anyone with read access to a repository can view a comment's edit history."; after a revision is deleted, "the person who made the edit and when they made the edit is still visible"
- [19] disruptive comments [official] https://docs.github.com/en/communities/moderating-comments-and-conversations/managing-disruptive-comments — undated (live doc): "The **edited** dropdown at the top of the comment contains a history of edits showing the user and timestamp for each edit."; "The initial comment (or body) of an issue or pull request can't be deleted."
- [20] sensitive data removal [official] https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository — undated (live doc): "GitHub Support won't remove non-sensitive data…"
- [21] Truffle Security [practitioner] https://trufflesecurity.com/blog/thousands-of-github-comments-leak-live-api-keys — 2023-09-27: "The drop down next to the 'edited' tag revealed prior versions, including the original containing the valid API key."
- [22] isaacs/github#954 [practitioner] https://github.com/isaacs/github/issues/954 — 2017-06-09: "Issues and comments on issues get edited. In a perfect world, they wouldn't need to…"
- **convergence (5 sources):** on a public repo the internet reads every revision; cleanup is manual and partial; non-secret business detail gets no support help. ⇒ the pre-send gate is the one control that works, and an `--exid` edit is gated as a create is

### L7 — github itself walls private text off from public at the issue level
- [23] issue transfer [official] https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/transferring-an-issue-to-another-repository — undated (live doc): "A private repository issue cannot be transferred to a public repository."
- **take:** precedent for a private-to-public guard

### L8 — fail closed: a read that cannot affirm safety takes the refuse path
- [24] Saltzer & Schroeder [academic] https://www.cs.virginia.edu/~evans/cs551/saltzer/ — 1975: "Base access decisions on permission rather than exclusion."
- [25] Wikipedia on the paper [practitioner] https://en.wikipedia.org/wiki/The_Protection_of_Information_in_Computer_Systems — undated (live doc): lists "Fail-safe defaults" and "Psychological acceptability"
- [26] OWASP: fail securely [practitioner] https://community.owasp.org/Fail_securely — undated (live doc): "A failure will follow the same execution path as disallowing the operation."
- [27] CWE-636 [official] https://cwe.mitre.org/data/definitions/636.html — undated (live doc): "…fall back to a state that is less secure than other options that are available…"; "safe defaults should be used"
- [32] fail-open vs fail-closed [blog] https://dev.to/khuepm/fail-open-vs-fail-closed-the-security-decision-you-make-without-realizing-it-15kl — July 3, year not shown: "Staying locked is fail-closed"
- [33] fail open access control [blog] https://security.unboundcompute.com/fail-open-access-control/ — 2026-08, low confidence: "…defaults to allow when something is missing, empty, or unexpected."; "Fail closed is safe by default."
- **convergence (6 sources):** ⇒ the read's catch returns `unreadable`, and `unreadable` takes the same path as PUBLIC

### L9 — an explicit, named confirmation flag is the accepted shape of a bypass
- [9] gh repo delete [official] https://cli.github.com/manual/gh_repo_delete — undated (live doc): "For safety, when no repository argument is provided, the `--yes` flag is ignored and you will be prompted for confirmation."
- [29] clig.dev (above): "allow scriptable confirmation via a flag like `--confirm="name-of-thing"`."
- [30] terraform apply [official] https://developer.hashicorp.com/terraform/cli/commands/apply — undated (live doc): "Skips interactive approval of the plan before applying."; "we recommend you first perform a plan operation and review the proposed changes"
- [31] kubectl delete [official] https://kubernetes.io/docs/reference/kubectl/generated/kubectl_delete/ — undated (live doc): "immediate deletion of some resources may result in inconsistency or data loss and requires confirmation."
- **convergence (4 sources):** a long, explicit flag that names the claim is normal. the promise slug names its claim in full

### L10 — content scanners are no substitute for the gate
- [34] about push protection [official] https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection — undated (live doc): "Anyone with write access to the repository can bypass push protection by specifying a bypass reason."
- [35] about secret scans [official] https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning — undated (live doc): covers "partner and provider secrets" (tool paraphrase)
- [36] arXiv 2307.00714 [academic] https://arxiv.org/html/2307.00714 — 2023-07-03: "no current tool has the coveted high precision and high recall scores"
- **convergence (3 sources):** scanners miss business detail (org names, routes, pr numbers) entirely. ⇒ the vision's out-of-scope call on a scanner holds

### L11 — distinct exit for a refusal; read fresh each send
- [37] POSIX shell exit status [official] https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_08_02 — undated (live doc): exit statuses "between 1 and 125"
- [17] REST best practices [official] https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api — undated (live doc): "You should not ignore repeated `4xx` and `5xx` error codes."
- **take:** the nudge exits 2 (this repo's constraint code); visibility is read per send, never cached

### L12 — error opacity vs name-the-fix
- [28] OWASP error cheat sheet [practitioner] https://cheatsheetseries.owasp.org/cheatsheets/Error_Handling_Cheat_Sheet.html — undated (live doc): "…a generic response is returned … error details are logged server side…"

## .within this repo

- the radio already shells every gh call through `runGhCommand` (argv, a timeout, the record's
  auth); the visibility read rides the same communicator, so auth and timeout behave as for a send
- tests fake gh with a stub executable first on PATH; each stub must answer `repo view` (default
  private) so extant journeys stay green
- the real demo repo `ehmpathy/rhachet-roles-bhuild-demo` is public: its push journeys need `--promise`

## .conflicts

- **[28] vs [29]:** [28] says return a generic error; [29] says name the flag. they serve different
  audiences (a web app's end user vs a cli operator). a cli names the fix — this repo's own rule
  (`rule.require.errors-name-the-fix`) agrees with [29]
- **fail-closed vs availability:** [24], [26], [27], [32], [33] refuse on error; a blanket deny can
  turn a blip into an outage. here a refusal is cheap (re-run, or pass the promise), so fail-closed wins
- **bind the promise to the repo?** [9] and [29] favor a confirmation bound to the named target
  (`--confirm=<name>`). the issue specifies one fixed literal. the push already names its target in
  `--into`, and the nudge prints the full command with that `--into`. a repo-bound value is a
  possible later guard, not this wish's ask
- **internal:** [11], [12] define it; no source rules on it. a policy call — F4, ruled

## .anti-patterns

- fail open on error, or on an absent / unknown field — [26], [27], [32], [33]
- read a 404 / 403 as "safe" — [10], [13], [14], [15], [16]
- cache visibility as truth — [17] (inference)
- an interactive prompt in automation — [3], [7], [29]
- a regex or entropy scan in place of the gate — [34], [35], [36]
- "edit it out later" as the remedy — [18], [19], [20], [21]

## .what this changes for the blueprint

- the visibility value set is closed: allow on PRIVATE / INTERNAL only; **any other value — an
  unknown future enum, an empty or absent field — is `unreadable`**, not just a non-zero exit (L1, L8)
- no cache, no prompt, exit 2 with the flag named (L4, L11)
