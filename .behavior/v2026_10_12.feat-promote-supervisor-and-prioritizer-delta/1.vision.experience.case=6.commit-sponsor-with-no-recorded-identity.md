# case=6 — bind a commit sponsor where no identity is recorded

**feel:** sharp → happy · **care:** critipath (a wrong identity binds, commits, and credits a human
who does not exist — silent and permanent in history)

## .narrative

a foreman asks for a commit sponsor. the supervisor clone runs
`rhx git.crew.commit.sponsor --tree svc-lessons.beav.feat-lesson-reminders --mode apply`. in the
source, a hardcoded default supplies the operator's own identity. the published skill ships none, and
reads the sponsor from a record a human made. none is recorded yet, so it refuses and prints the
command that records one. bert types
`rhx git.crew.commit.sponsor set --who "bert <bert@example.com>"` at a real terminal (at his claude
prompt, a `!` command has no tty, so he adds his words: `--approval 'yes, sponsor as bert'`). the clone
retries; the skill reads the record, sends the bind into the foreman's seat, and reads the pane back
to confirm. the clone could not have recorded bert itself: its permissions deny `set` and any write
to the meter file, and off a tty `set` demands bert's own words.

## .timeline (sketch)

```
given a published supervisor, its permissions init applied, and no sponsor recorded
  when [t0] the clone runs `rhx git.crew.commit.sponsor --tree <slug> --mode apply`
    then it exits 2: no commit sponsor recorded
    then the message names `! rhx git.crew.commit.sponsor set --who "<name <email>>"`
    then no seat is touched
  when [t1] the human runs `rhx git.crew.commit.sponsor set --who "bert <bert@example.com>"` at a real terminal
    then `.meter/git.crew.commit.sponsor.json` records that sponsor
  when [t1*] the human runs it at their claude prompt, as `! rhx … --approval '<their words>'`
    then the `!` command has no tty, so the bare form refuses and names `--approval`
    then with `--approval`, the record lands and holds their words verbatim
  when [t1'] the clone runs `rhx git.crew.commit.sponsor set …` itself
    then claude code refuses it by the permissions deny
    then even without the deny, off a tty `set` refuses unless `--approval '<the human's exact words>'` rides along, and records those words
  when [t2] the clone retries the bind
    then the skill sends `rhx git.commit.sponsor set --who "bert <bert@example.com>"` into the foreman seat
    then it reads the pane back and confirms the email landed
  when [t3] the clone runs `rhx git.crew.commit.sponsor get`
    then it reports the recorded sponsor and, where present, the words that opened it
  when [t4] the human passes `--sponsor` with another identity, at their terminal
    then that identity binds for this call only; the record is unchanged
  when [t4'] the clone passes `--sponsor` itself
    then off a tty it refuses unless `--approval '<the human's exact words>'` rides along — the
         override is a grant of identity, so it takes the same guard as `set`
    then the permissions deny covers `--sponsor` the same as `set`
```

## .fails safe

no identity in the shipped code, so no wrong default can bind. the refusal comes before any pane is
touched and names the one command that fixes it. two walls stand between a clone and a self-minted
sponsor: the permissions deny, and the tty guard inside the skill. both cover `set` and the
per-call `--sponsor` override alike, so the override is not a side door. `git config` is never read — on a
grove box it names a seaturtle, not bert.
