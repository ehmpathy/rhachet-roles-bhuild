# case=3 · an account's cap cannot be read

covers: R3, R9, C2, C3 · feel: sharp · care: critipath

## .narrative

a plan cap is published as a percent, not as a token count. so a token limit needs a
calibration: two reads of the cap % with a known cost-weighted burn between them give
tokens-per-%. until then, the meter knows the burn and does not know the wall.

the commander runs the read on a fresh account. the token rows do not guess. they print ⚪
`uncalibrated`, the affordable count is marked `≤ 5 (tokens unknown)`, and the render names the
one command that starts a calibration. a guessed cap would misprice every crew on the account,
so the meter refuses to supply one.

## .bdd sketch

```
given('[case1] an account whose cap % cannot be read')
  when('[t0] the commander runs `rhx git.grove.capacity`')
    then('each token limit reads ⚪ uncalibrated, never a number')
    then('the affordable count is marked an upper bound, with the reason')
    then('the calibrate command prints')
    then('the grove limits still print in full')

given('[case2] an account with one cap read and no second read yet')
  when('[t0] the commander runs `rhx git.grove.capacity`')
    then('the token limit stays ⚪ uncalibrated — one read cannot derive tokens-per-%')

given('[case3] two cap reads, and the 5h window reset between them')
  when('[t0] `rhx git.crew.tokens calibrate --account local` takes its second read')
    then('the 5h % fell while burn rose; the calibration refuses rather than derive a negative rate')
    then('it says the window reset, and names when a clean pair can be taken')
    then('the 7d pair, which did not reset, still derives')
  when('[t1] the commander runs `rhx git.grove.capacity` with C = 7d only')
    then('tokens.7d prints a number and may bind; tokens.5h stays ⚪ uncalibrated')
    then('the affordable count is a real answer on the 7d axis, marked an upper bound on the 5h axis')
```

### case3, as the supervisor lives it

the supervisor took local's first cap read before lunch: 5h at 71%, 7d at 40%. an hour of
crews later it runs the second read and expects token rows to fill in.

it sees the 5h row refused: `5h pair refused — the window reset between reads (71% → 12%
while 9.4M tokens were spent)`. the 7d row fills in from its own pair, which did not reset. the
render names the next step: `take a fresh 5h pair inside one window — next read after ~1h of
burn`. so the supervisor gets a 7d token limit at once, and knows exactly why the 5h one is
absent and when it can have it. it never sees a negative rate, and no crew count downstream
is priced off one.

```
🐚 git.crew.tokens calibrate --account local
   ├─ 7d   ✅ 1% ≈ 4.1M tokens (weighted)  · pair in one window
   └─ 5h   ✋ pair refused — the window reset between reads (71% → 12% while 9.4M spent)
      └─ next  take a fresh 5h pair inside one window, after ~1h of burn
```
