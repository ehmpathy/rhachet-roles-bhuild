# handoff v1 · to foreman · two credentials only the foreman holds

## .the ask

fill two github tokens into the ehmpath keyrack on this grove:

```sh
rhx keyrack fill --owner ehmpath    # add EHMPATH_BEAVER_GITHUB_TOKEN (envs test + prep) and BHUILD_DEMO_REPO_ACCESS_GITHUB_TOKEN
```

| key | what it gates today |
|---|---|
| `EHMPATH_BEAVER_GITHUB_TOKEN` | 16 red tests: `radio.task.push via gh.issues` acceptance (14), `getGithubTokenByAuthArg` [case3] and `genAuthFromKeyrack` [case1] integration (2) |
| `BHUILD_DEMO_REPO_ACCESS_GITHUB_TOKEN` | two skipped suites: `daoRadioTaskViaGhIssues` integration and `radio.task.pull via gh.issues` acceptance (F23) |

## .what was tried

- `rhx keyrack status --owner ehmpath` (2026-11-07): the rack on this grove holds
  `@all.camp.GITHUB_TOKEN` and neither key above
- the keyrack reports each as `absent`, not `locked`, so `rhx keyrack unlock --owner ehmpath
  --env test` (run by `git.repo.test` on each run) cannot reach them
- `git diff origin/main -- .agent/keyrack.yml src/domain.operations/radio/auth` is empty: this
  branch changed neither the declaration nor the reader, so the red is the grove's rack, not code
- the suites forbid the default gh login by their own `.critical` note, so the camp token or an
  ambient `gh` session is no substitute

## .why it is foreman-only

a keyrack fill is a credential provision, a human gate (`rule.forbid.self-grant-human-gates`).
