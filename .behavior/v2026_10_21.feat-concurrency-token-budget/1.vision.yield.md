# 1.vision.yield — how many crews can the fleet afford, and what raises it

## .the deliverable

two things, in this order:

1. **an instrument** — one read-only verb that answers, per grove × account, how many crews of
   each kind fit, which limit binds, and which levers raise it
2. **the measured answer** — that verb's output, read twice in different conditions on both
   groves, written down as the report the commander asked for

the instrument comes first because the answer decays: crews, accounts, and levers change
weekly. a number without the verb that remeasures it is stale by the next release.

### the contract (sketch)

| verb | role | does |
|---|---|---|
| `rhx git.crew.tokens` | supervisor | **cured, not measured around**: reads every claude config dir (`~/.claude` + each worktree's `.agent/.actors/*/brain/.claude`), on local and on named groves; groups seats into crews by kind; cost-weights the burn; survives a closed pipe; `calibrate` derives tokens-per-% from one cap read plus its window reset time, or from two reads where no reset time shows — summed over every seat on the account, across groves (F2) |
| `rhx git.grove.capacity` | supervisor | composes `git.crew.tokens` + `git.grove.saturation(.spend)` into four limits per crew kind, marks the lowest as the one that binds, prints the affordable count and the exchange rate |
| `… --grove <g> --for <kind>` | | the sprout gate: free slots, or exit 2 with the fellable crews and the seed move. a grant **holds** its slot until the sprout boots or the hold lapses, so two concurrent asks cannot both win the last slot (case=2 case3, A7). **not asked by the wish** — kept because it is the same computation with an exit code; the wisher may cut it (F7) |
| `… --levers` | | levers ranked per grove by gain in crews against the limit that binds there, in three tiers by evidence (below); each row carries its read count |
| `… --json` | | the same records for a tick |

the formula, per grove × account × kind. an account's token limit is shared by every seat on
it, on every grove (A3); burn is weighed per model and cache tier, and taken per turn where the
grove was stalled (A5):

```
limit.tokens.<window> = (cap headroom in the window, cost-weighted) / (burn per crew-hour × hours left in window)
limit.grove.ram       = (ram usable − baseline)  / ram per crew
limit.grove.cpu       = crews before cpu stall life crosses the 🟡 line
affordable            = min(all four)
```

burn per crew-hour is the **observed average** over a window long enough to hold gates, work,
and review ladders, so the duty-cycle mix is folded in by the data, never modeled. a per-state
breakdown (gate · work · ladder) prints beside it where seat state is derivable; it answers
"what if more crews park", and the affordable count does not lean on it.

### the lever tiers — measured or estimated, never unmarked

the wish asks for each lever's "measured or estimated gain". the repo rule forbids a rank off
a config or a single window. both hold if the estimate is built on a measured cost:

| tier | gain is | may rank? |
|---|---|---|
| **measured** | the lever landed; before/after, 2+ reads in varied conditions | ✅ |
| **estimated** | the cost the lever targets is measured (2+ reads), times the share it would remove (stated, with its basis) | ✅ within its tier, never above a measured row |
| **unmeasured** | no read of the cost it targets (a config, an issue thread) | ❌ listed, never ranked |

most candidate levers sit in the **estimated** tier today: none is built, but the cost each
targets can be read now. two examples: hook forks/s (hook `durationMs` is in every
transcript), and fork cache-writes (`isSidechain` + `cache_creation` per line).

## .the outcome world

**before.** the commander asks "can we run more?" and gets a guess. the meter at hand is blind
to crews under `_worktrees` (per the wish; likely because each crew's transcripts live in its
worktree's actor dir, not in `~/.claude`); it
carries no cost weight and no % of cap; it died under load. grove health is read with a
separate verb that knows naught of tokens. nobody can say which wall the fleet hits first, so
every lever is argued on taste.

**after.** one call prints, per grove, four limits and the one that binds. the commander learns
(in the sketch) that 0901 is ram-bound and local is cpu-bound — and that neither is
token-bound today. the lever table then makes the next move obvious: on a ram-bound grove, the
fork cap buys crews and the small-context fork buys none, however large its token cut.

**the aha.** a lever only pays on the axis that binds. the largest token cut on record (cache
writes ≈ half of cost-weighted spend, one window) can buy **zero** crews on a grove where ram
binds. the table shows `+0 crews` beside a large token cut (40% in the sketch), and the
commander funds the other lever.

⚠️ every count in the case renders is illustrative. the only measured numbers in this stone are
the wish's 1h window and this box's `/proc` read in `.groundwork`.

**a day.** the supervisor's tick runs `git.grove.capacity --json`. before each sprout it asks
for a slot; a full grove returns the fellable crews and the seed move. once a week the
commander reads `--levers`, funds the top ranked rows, and the next week's second read either
promotes their gain to measured or demotes it.

## .mental model

- to a friend: *"it tells you how many crews fit on each box, which wall you hit first, and
  which fix moves that wall."*
- the analogy: a freight dock. trucks (crews) are limited by whichever runs out first — bay
  space (ram), forklift time (cpu), or fuel budget (tokens). a cheaper fuel deal does not
  park one more truck when the bays are full.
- their words vs ours:

  | the commander says | we say |
  |---|---|
  | how many can I run | affordable count |
  | what's the bottleneck | the limit that binds |
  | what would let us run more | levers, ranked by gain in crews |
  | a director costs a lot | exchange rate: 1 directive ≈ N behavior |

## .evaluation

| goal (from the wish) | met by |
|---|---|
| behavior crews affordable, per grove × account | case=1, the `affordable` row per kind |
| directive crews affordable, per grove × account | case=1, the same row, `directive` |
| ranked levers with measured or estimated gain in crews | case=5: measured and estimated tiers both rank, against the limit that binds; read counts shown |
| both walls: tokens (5h + 7d) and grove (cpu, ram, forks/s) | four limits per kind; forks/s feeds the cpu limit via `saturation.spend` |
| cure `git.crew.tokens` or measure around it, and say which | **cure** — see fulcrum F1 |

**pros.** one verb, one formula, the axis that binds named on every render; it composes the
grove instruments that already exist rather than a second path; every rank carries its read
count, so a one-window number cannot pose as a ranked fact.

**cons.** the token limit rests on a calibration we have not yet proven possible (F2). the
per-state breakdown needs a seat-state signal; without one it is absent, though the affordable
count still stands on the observed average. the answer is a frontier, not one number, which
asks more of the reader.

**pit of success.**
- an unread grove yields no slot (case=4), never a guess
- two asks for the last slot cannot both win: a grant holds it (case=2)
- an uncalibrated cap yields ⚪, never a number (case=3)
- a lever is ranked only on a measured cost: its own before/after, or the cost it targets
  (case=5). an unmeasured lever is listed, never ranked
- a partial read marks its total a lower bound and names what it could not read (case=4)
- a closed stdout exits clean (R6), so `| head` cannot kill a tick

## .what is awkward

- **the answer is a frontier.** "4 behavior or 1 directive" is honest, and a weaker read than
  one number. the exchange rate is the bridge; it may still read as a hedge
- **the token limit depends on a % we may not be able to script.** if Q2 resolves to "no", the
  token half of the answer rests on hand reads, and the verb's freshest number is the grove's
- **"park at a gate" looks like a lever and may not be one.** a parked crew keeps its process,
  so it frees tokens and holds ram. on a ram-bound grove the lever that pays is a fell, which
  costs the crew its context
- **the sweep itself costs.** a meter that reads every transcript on a 🔴 grove joins the queue
  it measures. reads must stay counter-shaped and bounded (the 38,600-fork lesson)
- **the two walls are not independent.** a saturated grove slows every turn, which lowers each
  crew's token burn per hour (A5). so a grove lever can raise token spend: free the cpu, and
  each crew burns faster. `min()` of four limits read apart hides this; the verify step must
  re-read the token limit after any grove lever lands
- **cost weights are borrowed from api price.** if a plan weighs differently, every limit
  shifts together; the rank survives, the counts do not
