# 1.vision.experience.dimensions — radio.recorder

the axes a `radio.task.push` experience varies over, once every attempt is transcribed first.

## .the dimensions

| # | dimension | values | why it varies independently |
|---|-----------|--------|-----------------------------|
| D1 | **actor** | `clone` (a driver mid-route) · `human` (at a terminal) · `system` (a cron or ci job) | who pushes. a clone cannot lift a block; a human can; a system can neither lift nor read a teach line. same push, different next move |
| D2 | **gate** at attempt, **per target repo** | `open` · `blocked:radio.uses` · `blocked:upstream` (401, offline, rate-limit) | the state of the path out. set by a human (radio.uses) or the world (upstream), never by the task. `radio.uses` decides per target org/repo, so each held record carries its own gate (see inventory C20) |
| D3 | **other held records** at attempt | `none` · `some` (≥1 undelivered record **besides** this task) | what else the recorder holds. this task's own record is D4's business, never D3's — so the two axes cannot overlap |
| D4 | **this push's record** | `new` · `queued` (same push, still undelivered) · `landed` (upstream already reflects it; local record may lag) | whether this push is a first attempt or a repeat. drives idempotency. applies to both kinds: a create is keyed `(repo, title)`, an update `(repo, exid, status)` |
| D5 | **route** | `bound` · `unbound` · `bound-to-many` | where `.radio/` lives. the wish places it in the route; a push from outside any single route must still land somewhere or refuse loud |
| D6 | **push kind** | `create` (`--title`) · `update` (`--exid --status`) | the same command carries both. F5 (wisher): both are recorded and held. an update differs from a create in one place — its replay can meet a task someone else moved meanwhile (inventory U1–U5) |

## .why these are orthogonal

- **gate ⟂ other held** — three others can meet an open gate (drain) or a shut one (grows to four).
- **gate ⟂ this task's record** — a `landed` record can meet a gate that shut after it landed.
- **other held ⟂ this task's record** — each D4 value meets each D3 value: a re-push of a queued
  task with no others held, or with three others; a first push with none or with some. D3 counts
  **others** only: were this push counted in it, `none × queued` could not occur, and the two axes
  would correlate.
- **actor ⟂ gate** — a human, a clone, or a cron can each hit a block; they differ only in who
  can lift it.
- **route ⟂ all** — the recorder's home is a place, not a state of the push.
- **push kind ⟂ gate** — a claim meets a shut gate as readily as a create does.
- **actor ⟂ other held** — a cron can meet a backlog as readily as a clone.
- **actor ⟂ this task's record** — a human can re-push a held task as readily as a clone can.
- **actor ⟂ push kind** — each actor can create or claim.
- **other held ⟂ push kind** — a claim can meet a backlog of held creates, or none.
- **push kind ⟂ this push's record** — an update too can be a first attempt (`new`), a repeat of
  a held claim (`queued`), or a claim upstream already reflects (`landed`). D4 keys on the push,
  not the task, so every pair occurs.

## .dimensions considered and folded

| candidate | verdict | why |
|-----------|---------|-----|
| **channel** (`gh.issues` · `os.fileops`) | folded into D2 | a channel matters only through whether its gate is open. `os.fileops` has no upstream to fail, so `blocked:upstream × os.fileops` is impossible by nature |
| **drain trigger** (explicit `--flush` vs next push) | folded — not a dimension | the wish removes the choice: the next push that gets through drains — a create or an update alike. a flush verb is an alias of "push with an open gate", not a separate experience |
| **a later push occurs** (`fires` · `never fires`) | kept as one cell, not an axis — **A3** | the timeline after a gate lifts. `fires` is every core cell; `never fires` is the one path off it: the backlog idles. one real cell, so it is walked as a row rather than multiplied across the product |
| **moment** (`a push` · `a stop` · `a list`) | kept as rows, not an axis — **S1–S4**, **L1–L4** | every core cell happens at a push. the recorder speaks at two other moments, and both only read: a clone's stop (one line, or naught) and a human's `rhx radio.task.held` (the whole backlog, even when empty — surfaced at verification). each varies on just D3 (held or none) × D2 (gate), walked as the stop row and the list row |
| **auth** (`as-human` · `as-robot:via-keyrack(…)` · `as-robot:env(…)` · `as-robot:shx(…)`) | folded into D2, per record — like channel | auth matters only through whether its credentials can be derived at send time. if they cannot (keyrack locked, token refused), that record's gate reads `blocked:upstream` with reason `upstream:auth`. the per-record twist — a held record keeps its own auth, never borrows the push's — is cell **C22**, demoed in case=3 `[t3]` |
| **concurrency** (two pushes on one worktree at once) | kept as cells, not an axis — **C19**, **C23** | see below |
| **body source** (`--description "…"` · `--description @stdin`) | kept as one cell, not an axis — **C24** | surfaced at verification. the source matters only where the gate shuts: stdin is a stream read once, so transcribe-first must read it before the gate, or a held record keeps no body. on an open gate both sources deliver alike, so the one sharp pair is `@stdin × blocked`, demoed in case=2 `[t3]` |

### why concurrency gets cells, not an axis

concurrency as an axis would double every cell with a `concurrent` twin. on this surface the twin
differs in exactly two places, both about shared state, so both are named as cells instead:

- **C19** — two drains race over one backlog. guarded by X2 (upstream findsert): worst case one
  redundant findsert, never a duplicate issue.
- **C23** — one push reads a record another push is mid-write on. guarded by an invariant for the
  criteria stone: a record is written whole (temp file + rename), so a reader sees the old record
  or the new one, never half.

every other cell is concurrency-blind: its outcome depends on the gate, the record's status, and
the route — each read atomically per record.

## .the product — and why it collapses to the walked rows

`D1 × D2 × D3 × D4 × D5 × D6` = 3 × 3 × 2 × 3 × 3 × 2 = **324 tuples**.

the inventory walks **D2 × D3 × D4 = 18** core cells for a create, each verdicted. the other three axes are
walked as their own rows, because each changes **one** observable and leaves the core outcome
untouched. the collapse, stated per axis so it can be checked rather than trusted:

| axis | what it changes | what it leaves alone | so each cross-product |
|------|-----------------|----------------------|-----------------------|
| D1 actor | the lift line (a clone is told a human must lift; a human is told the command; a system gets the same line, unread) | record, status, drain, idempotency — the push code never branches on who ran it | = the core cell's outcome + the actor's lift line. verdicted as rows A0–A3 |
| D5 route | the directory the record lands in | status, drain order, gate, idempotency | = the core cell's outcome, at `$route/.radio/` or `.behavior/.radio/`. rows R1–R3 |
| D6 push kind | the record key, and one replay hazard: an update can meet a task another actor moved meanwhile | record, gate, drain order, idempotency — the same as a create | `create × any` = the core; `update × any` = the core's outcome for a claim, plus the replay hazard — rows U1–U5 |

e.g. `human × unbound × open × some others × new` = C4's drain, recorded at `.behavior/.radio/`,
with no lift line (gate open). no cross-product yields an outcome the rows do not already name.
