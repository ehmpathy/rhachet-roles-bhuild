# 🌙 dream: a clone sees the texts held for it, not only the ones it sent

kind: feat · owner: rhachet-roles-bhuild (dispatcher phone) · caught 2026-10-25

## .the cue that fired

the live demo on `beav/feat-phone-text`: two peers replied to this clone while its pane was
mid-turn. `clone say` withheld both, so both replies sat QUEUED. `rhx phone.text get` on the
recipient showed no inbound text at all; only the tree daemon log named them:

```
text 2a6ca7b6… → …/clone=65486ed8…: QUEUED peer screen unrecognized
```

## .the gap, precisely

a QUEUED text lives in the sender's mailbox only; the recipient's `in` copy is written at
delivery. so `phone.text get` reads the recipient's mailbox and can not know a text waits for it.
a busy clone has no way to learn that a reply is held until its turn ends.

## .the shape of the fix

- same tree: `phone.text get` also scans the tree's other mailboxes for `out` records QUEUED to
  this seat, and lists them as `held for you · <reason>` beside the thread. one read per mailbox,
  the same scan the daemon's `isMailboxQuiet` already does
- cross tree: the sender's mailbox sits in another tree. either the send writes a `held` stub
  into the peer tree at QUEUED time (F6 already writes there at delivery), or `get` reads the
  trees its contacts name. the stub keeps reads local; it needs a settle step to clear it
- clamp: a held reply to a mid-turn seat shows in that seat's `get`, then leaves the list once
  DELIVERED

## .why it is not done in this round

the same-tree half is small, but a half that is silent for cross-tree texts would mislead more
than it helps; the cross-tree half adds a write into a foreign tree at send time, a scope call
beside F6 that the commander should see first.
