the lift dropped `ecowork.integration.test.ts` into a repo with two test gates, and
`jest.integration.config.ts` auto-discovered it. it came up **37 failed / 309 passed / 346 total**.

the arithmetic then said the red is not the port's:

| measured | figure |
|---|---|
| our copy, after the sqlite repair | 37 failed / 346 total |
| the source clone + our copy, before it | 77 failed / 692 total |
| 692 ÷ 2 | **346** — the same suite, twice |

⇒ **the suite fails ~40 of its own tests in the source notebook, today.** the source notebook has zero github workflows, so
no gate ever asked it to be green.

🔴 **the sharper cue: I mis-diagnosed this once already.** every failure i sampled carried the
`node:sqlite` experimental notice in its received stderr, so i read it as the cause of all ~38. it
was the cause of about **three**. the rest carried it as a passenger. ⇒ `term=partial-audit`: a read
complete over the scope it chose, stated as a verdict about the whole.

## .the gap, precisely

### class 1 — five families grade the HOST REPO (`rule.require.hermetic-tests`)

| family | what it reads |
|---|---|
| `[case39]` the committed store in this repo | the host's committed `.eco/*.csv` mirror |
| `[case53]` the text git carries | the same mirror, via `git ls-files` |
| `[case45]` the ignore rules git carries | the host's `.gitignore` |
| `[case46]` the pre-commit hook | the host's `.husky/pre-commit` |
| `[case56]` the programs that may open the store | a walk over the host's tree |

these cannot pass anywhere but the source notebook, because the source notebook's own `.eco/` store is their subject.

### class 2 — a plant that does not hydrate (13 families)

`[case12]` `[case13]` `[case14]` `[case22]` `[case23]` `[case26]` `[case27]` `[case31]` `[case32]`
`[case33]` `[case40]` `[case48]` `[case59]`.

each scene writes rows into `priority.csv` beside a temp db, then invokes `eco.priority set` and
gets back the refusal for a row the store has never seen:

```
a new priority needs --sev and --urg and --what
   └─ fix: rhx eco.priority --help
```

🟡 **hypothesis, unproven.** `asStorePath = (dbPath, table) => join(dirname(dbPath), table + '.csv')`
puts the mirror exactly where the plant writes, so the path is right. the likelier gap is that
hydration derives its table set from `sqlite_master` and no-ops where **no db yet exists**. one read
of `asStoreHydrated` settles it. it is environment-independent, which fits the source copy's
identical red.

## .the shape of the fix

1. **read `asStoreHydrated`** and settle class 2's cause. if it is the no-db no-op, one repair
   clears 13 families at once — the cheapest half by far, and it is a **product** defect rather than
   a test one: a fresh clone with text and no db is the sanctioned door
   (`define.invariant.eco.the-csv-is-truth-the-db-is-a-cache`).
2. **give class 1 a fixture store.** each of the five families wants *a* repo with a committed
   `.eco/` mirror, a `.gitignore`, and a pre-commit hook — not *this* one. stage one in a temp git
   repo (`genTempDir` + `git init`) and point the walk at it.
3. **then gate it.** once green, it needs no exclusion and `F9` dissolves.

⚠️ **do not reach for a skip.** `rule.forbid.failhide` names it directly — *"skips — hidden lies
that pass ci"*. while the suite is out of the gate it owes a **ratchet** on the failure count, so a
38th goes red.

## .why it is not done in this round

**SAFE?** no. step 1 edits `ecowork.db.mjs`'s hydration path — the module every `eco.priority` call
goes through, with 309 green clamps over it. step 2 rewrites five case-families' scenes.

**CLEAN?** no. it ripples into the module, the suite, and the fixture corpus, in a diff already at
77,742 lines.

⇒ both answers are no, so it defers — and a defer for **dirt** owes a fulcrum beside the dream
(`rule.always.fix-forward-under-scouts-honor`). that is
`.fulcrums/inventory.of=fulcrums.case=F9-ecowork-suite-gate-membership.md`.

## .what already landed, and stands on its own

independent of all of the above: a human who runs `rhx eco.priority get` should not meet a note
about a node internal (`rule.forbid.surprises`), and it cleared the `stderr: ''` class. it simply
repaired three tests rather than thirty-eight.
