# 🌙 dream: bhrain exports the review scope walk, so a guard author can prove a lane's scope

kind = reseed · owner = ehmpathy/rhachet-roles-bhrain · caught 2026-11-23

## .the cue that fired

the 5.1 peer review of the trust-of-wisher-how route flagged `initBehaviorDir.visionScope.integration.test.ts` as a scope leak: it `require`s `rhachet-roles-bhrain/dist/domain.operations/review/getOneReviewScope.js` by path, because the package's exports map hides that function.

## .the gap, precisely

a repo that ships guard templates owes a proof that each peer lane reads the files it should. the only way to compute a lane's scope as bhrain does is `getOneReviewScope`, and bhrain does not export it. so the consumer reaches into `dist/` and hand-declares the slice of the type it reads. the suite fails loud if the module moves (the `require` throws), but the type slice can drift in silence, and the reach is a private path no semver protects.

## .the shape of the fix

in bhrain: export the scope walk from a public entry (e.g. `rhachet-roles-bhrain/cli/review`, beside `parseReviewArgs`), with its input and output types, and type `parseReviewArgs`'s `polluters` and `join` as their literal unions. then in bhuild: import it, delete the `require`, the `GetOneReviewScope` slice, and the two `as` casts in `getAllLaneScopesOfStone`.

## .why it is not done in this round

the fix lives in another repo. the reach predates this route; this route only calls the extant walk for a second stone.
