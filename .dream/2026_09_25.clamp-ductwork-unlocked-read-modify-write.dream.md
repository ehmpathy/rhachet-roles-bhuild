## .the gap, precisely

`src/domain.roles/supervisor/skills/work/ductwork.sh` holds three unlocked
read-modify-write cycles against a **shared** json registry under `$DUCTWORK_DIR`:

| lines | function | the cycle |
|---|---|---|
| 100–111 | `__duct_register_host` | a truncate-then-write `cat > "$file"` — no read, and no lock either |
| 161–184 | `__duct_register_duct` | `jq -c '.' "$file"` → `jq '. + {…}'` → `printf > "$file"` |
| 207–223 | `__duct_set_duct_session_id` | identical shape, merges `sessionId` |

each is a check-then-act with a gap between the read and the write, and **the registry is
shared by every clone on a grove**. two concurrent writers interleave like so:

```
A: prior=$(jq -c '.' duct.json)        # {"host":"h","createdAt":1}
B: prior=$(jq -c '.' duct.json)        # {"host":"h","createdAt":1}
A: printf '%s' "$next" > duct.json     # {"host":"h","createdAt":1,"sessionId":"aaa"}
B: printf '%s' "$next" > duct.json     # {"host":"h","createdAt":1}   ← A's write is GONE
```

⇒ **B's write is a lost update, and it is silent.** no error, no exit code, no log line.

### 🔴 why the lost field is the expensive one

`sessionId` is not decoration. its own header says what it buys:

> *"a duct that hosts a clone carries that clone's IDENTITY, so a crash is recoverable:
> `claude --resume <uuid>` addresses the exact conversation. without it the only lever is
> `--continue`, which resolves by cwd-recency — and a mechanic and a foreman SHARE one
> worktree, so 'the most recent conversation in this directory' is a race between the two
> roles, decided by whoever spoke last."*

⇒ a lost `sessionId` degrades a **precise** recovery into a **racy** one — and it degrades
it at exactly the moment recovery is wanted. worse, the header also declares that an absent
`sessionId` is **meaningful**: a duct with none is a bare shell *by design*, so a reviver
leaves it alone. ⇒ a lost update does not merely erase data; it **converts a clone's duct
into a foreman's duct in the eyes of every reader**, and the reviver then correctly refuses
to revive it.

### the window is real, not theoretical

`crewwork.sh` opens a crew's seats in a loop, and the whole point of a crew is that its
seats come up together. the writes are milliseconds apart on the same registry.

## .the shape of the fix

`flock` on the registry file, around each read-modify-write. the file is already the unit of
mutation, so the lock has an obvious subject and needs no new state:

```bash
__duct_with_lock() {
  local file="$1"; shift
  mkdir -p "$(dirname "$file")"
  exec {fd}>>"$file.lock"
  flock "$fd"
  "$@"
  exec {fd}>&-
}
```

then wrap the three cycles. two bounds to respect:

- ⚠️ `flock` is **not** on macos by default (it is util-linux). the groves are linux, so the
  common path is covered — and `ductwork` also runs on a human's laptop. a portable
  fallback is `mkdir`-as-mutex, which is atomic on every posix fs.
- 🟡 a write-then-rename (`printf > "$file.tmp" && mv "$file.tmp" "$file"`) makes each write
  **atomic** and does NOT close this gap — it removes torn reads, and a lost update is not a
  torn read. ⇒ rename is worth a place beside the lock, never instead of it.

## .the clamp it owes

a regression test that goes red under the un-fixed code: spawn N concurrent
`__duct_set_duct_session_id` calls against one registry row, then assert **every** id landed.
the extant `ductwork.integration.test.ts` drives the real lib against a temp `DUCTWORK_DIR`,
so the harness for this already exists — only the concurrent driver is new.

⚠️ the clamp must be dogfooded: revert the lock, watch it go red, restore, watch it go green.
a concurrency test that passes without the fix exercised no interleave at all, and that is
the common failure mode for this shape.
