# 🌙 dream: make `decompose.behavior` fail loud when its brain call returns naught

| field | value |
|---|---|
| **kind** | `adopt` — the suite lives in this repo, `role=decomposer` |
| **owner** | `ehmpathy/rhachet-roles-bhuild` |
| **caught** | 2026-09-25 |
| **route** | `.behavior/v2026_09_22.feat-lift-supervisor-and-prioritizer-roles` |

## .the cue that fired

a 17-suite integration run went red on exactly one test:

```
● decompose.behavior.sh › given: [case6] --mode apply with valid plan file
    Expected substring: "user-auth"
    Received string:    ""
```

re-run in isolation, the same suite: **14 passed, 0 failed, 89s.**

⇒ so it is load-dependent, not a real regression. **1972 passed, 1 failed** under parallel
load; **14 passed** alone.

## .the gap, precisely

`result.stdout` was the **empty string**, and the assertion that caught it was
`toContain('user-auth')`.

🔴 **the assertion is the wrong instrument for the failure that actually occurred.** it reports
*"the output lacked a token"*, when the truth is *"there was no output at all"*. those are
different defects with different causes:

| the true state | what the failure says |
|---|---|
| the brain answered, and got the decomposition wrong | `Expected … Received ""` |
| the brain never answered — timeout, quota, contention | `Expected … Received ""` |

⇒ a reader of the ci log cannot tell a **content** defect from an **absent-call** defect, so the
first instinct is to debug the decomposer's prompt — which is sound logic about the wrong event.

## .why it is more than a nitpick

`rule.forbid.failhide` is not violated (it does fail), but `rule.require.failloud` is: the error
names a symptom and not the cause, so it teaches no fix.

and the cost is concrete — **this is a flaky gate on a required workflow**. a flake that reports
a cause which misleads gets investigated as a real defect once per occurrence, by whoever is on
the PR.

## .the shape of the fix

an anti-vacuity assert **before** the content assert, in the same `then` chain:

```ts
// ANTI-VACUITY: an empty stdout is an absent brain call, never a wrong one —
// assert the call happened before we grade what it said
expect(result.stdout).not.toEqual('');
expect(result.exitCode).toEqual(0);

expect(result.stdout).toContain('user-auth');
```

two parts, each load-central:

1. **the empty check** — separates *"never answered"* from *"answered wrong"* in the log
2. **the exit code** — a non-zero exit with empty stdout names a crash rather than a timeout

⚠️ **this does not fix the flake.** it makes the flake *legible*, which is the precondition for
a real diagnosis. the root cause is likely resource contention on a live brain call under
17-suite parallelism, and that is a separate question — `maxWorkers`, a retry, or a scope move.

## .why it is not done in this round

**SAFE?** yes — it adds asserts to a test in a role this branch does not touch.

**CLEAN?** 🔴 no — `src/domain.roles/decomposer/` is outside this lift's diff entirely, and the
branch already carries 77,742 lines. a decomposer-suite edit smuggled into a supervisor and
prioritizer graduation is the exact scope creep `rule.require.review-test-changes` forbids.

⇒ one answer is no, so it defers (`rule.always.fix-forward-under-scouts-honor`).
