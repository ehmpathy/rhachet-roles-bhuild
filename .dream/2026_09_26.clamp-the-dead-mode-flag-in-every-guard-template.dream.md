# 🌙 dream: clamp the dead `--mode hard` flag in every guard template

- **kind** = `clamp`
- **owner** = `ehmpathy/rhachet-roles-bhuild` · `role=behaver`
- **caught** = 2026-09-26

## .the cue that fired

nine peer lanes of `.behavior/v2026_09_22.feat-lift-supervisor-and-prioritizer-roles`, stone
`5.1.execution.from_vision`, returned `✋ prompt exceeds 75% of context window` for four rounds
(i001→i004) without a line read. the diagnosis reached the lane binds — and then reached one
step further, to a flag none of them actually had.

## .the gap, precisely

every guard template ships its review lanes with `--mode hard`:

```
run: $rhx review --repo bhrain --mode hard --rules '…' --diffs since-main …
```

`rhx review --help` documents exactly:

```
--rules --paths --paths-with --paths-wout --diffs --join --refs
--optional --conversation --output --focus --goal --brain --open
```

🔴 **`--mode` is not among them**, and it has never once had an effect.

measured 2026-09-26: **51 lines across the 12 templates** in
`src/domain.operations/behavior/init/templates/`.

### ⚠️ .this dream first stated the WRONG MECHANISM — corrected at the executable line

the first version of this file said *"an unknown flag is dropped in SILENCE — no error, no warn
(the same quiet-drop class already caught for `--paths-with` brace globs)"*. **that is false**,
and the check that falsified it is the one `rule.always.trust-but-verify` asks for:

| the claim | what `review.js` actually does |
|---|---|
| `--mode` is unknown | 🔴 `FLAGS_KNOWN` (`:155-174`) holds `mode` **deliberately**, beside `skill` and `repo` |
| an unknown flag is dropped in silence | 🔴 `:265-272` **fails loud**, `exit 2`, and cites `rule.forbid.failhide` by name |

and the code says why, at `:148-153`: `--skill`, `--repo`, `--mode` are the **rhachet
dispatcher's** own flags. the dispatcher reads them to pick which skill to boot, so they arrive at
`review()` too, and the allowlist tolerates them on purpose — *"the allowlist's job is to catch a
TYPO in a flag `review()` itself acts on, never to re-litigate the dispatcher's own contract"*.
its note even records the round that lesson was learned: every guard-run lane refused with
*"unrecognized flag(s): --skill, --repo, --mode"* the round the allowlist shipped without them.

⇒ **so `--mode hard` is inert BY DESIGN, not by a silent drop.** the conclusion (delete it) is
unchanged; the reason it was believed was wrong, and a wrong reason left on record sends the next
reader to hunt a failhide that does not exist.

⚠️ and the correction matters beyond this file: the same false mechanism was written into the
route's guard comment, its `ergo-friction-hazards` `.taken`, and the execution yield. **a claim
restated in four places is a cache in four places**, and that is the shape the route's own
verification list already warns about.

⇒ the harm is not that `hard` is wrong — `--focus`'s default is `push`, which is what `hard`
meant to say, so behavior today matches intent by coincidence. the harm is that **the control
a driver reaches for when a lane overflows is inert**, and the reach looks like it worked.

## .the shape of the fix

two separable changes, and they must not be conflated:

| # | the change | blast radius |
|---|---|---|
| 1 | **delete** the dead `--mode hard` | none at runtime — it is already inert |
| 2 | **add** `--focus push` or `--focus pull` deliberately, per lane | every future route |

⚠️ change 2 is the one that matters and the one that must not be made blind. `pull` is right
where a lane's corpus is large (`review.tactics`: >50 files, or a window over 60%) and wrong
where a rubric needs the full text in one shot to reason across files. that call is per-rubric,
not global — so a sweep that sets all 51 to one value would be the same mistake in a new form.

and `rule.require.guard-variant-consistency` binds the fix: `1.vision.guard.{heavy,light}` and
`3.3.1.blueprint.product.guard.{heavy,light}` are variant pairs, and
`5.1.execution.{from_vision,phase0_to_phaseN}.guard` are the execution pair. a fix to one
member of any pair is a defect.

🟡 **a clamp is owed beside the fix**, since this is the second silent-flag-drop found in this
repo: a test that greps every `$rhx review` line in `templates/*.guard*` and asserts every flag
it carries is in the skill's own `--help` output. that turns a class of typo into a red gate
rather than a four-round stall.

## .why it is not done in this round

the SAFE/CLEAN test (`rule.always.fix-forward-under-scouts-honor`), both halves:

- **SAFE? change 1 yes, change 2 no.** to delete an inert flag changes no behavior. to set
  `--focus` changes how every future route's reviews are assembled, and the right value differs
  per rubric — a call that needs a per-lane read, not a sweep
- **CLEAN? no.** 51 lines across 12 files in `src/domain.operations/behavior/init/templates/`,
  a subtree this route does not otherwise touch. it would ride into a PR already named
  *"too big to review well"* in its own yield, and it would arrive as an unrelated 12-file diff

⇒ change 1 alone is safe-but-unclean; change 2 is unsafe. by the rule's own table both defer,
and the deferral of a DIRT call owes a fulcrum beside this dream.

🔴 **and the route's own guard was repaired in place regardless**, because that file IS this
route's diff: all nine of its static lanes now run `--focus pull`, with the measurement and the
`--help` list recorded in the guard's own comment. so the instance is fixed and the CLASS is
what defers.
