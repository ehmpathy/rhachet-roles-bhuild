# 🌙 dream: calibrate a cap from one ledger read plus its reset time

kind: feat · owner: bhuild supervisor (`git.crew.tokens calibrate`) · caught 2026-11-06

## .the cue that fired

self-review `behavior-declaration-adherance` on route `v2026_10_21.feat-concurrency-token-budget`:
the vision names two calibrate paths; the build ships the two-read one alone.

## .the gap, precisely

`calibrate` needs two cap rows per account (a % rise over a span). a fleet whose cap ledger holds
one row per account reads ⚪, though one row with `resets_at` already fixes when the window began
(`resets_at − 5h`), so `used_percentage` against the burn since then yields tokens per %.

## .the shape of the fix

- in `calibrate`, per account and window, where only one row exists and `resets_at` is known:
  window start = `resets_at − 5h` (or `− 7d`); burn = the account's weighted burn over
  `[window start, read time]`; tokens per % = burn / `used_percentage`
- the 5h path is cheap (a 300-min scan); the 7d path is a 10,080-min scan — gate it behind a flag
  or a calm box (cpu stall under 🟡), never on a 🔴 grove
- the verdict names its path: `calibrated (one read)` vs `calibrated (two reads)`
- clamp: a fixture ledger with one row and a reset time calibrates; with one row and no reset time
  stays ⚪

## .why it is not done in this round

safe, not clean: a second verdict path through `calibrate` and its render, and the 7d scan is the
grove cost this route measures. the two-read path lands the caps within minutes of the seat
restart. fulcrum F13.
