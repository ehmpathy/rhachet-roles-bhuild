# 🌙 dream: land the husky + rhachet upgrade in its own pr, with the defects its review found

kind = chore · owner = whoever ran the upgrade in the trust-of-wisher-how worktree · caught 2026-11-23

## .the cue that fired

the 5.1 peer review of the trust-of-wisher-how route raised 6 blockers and 4 nitpicks. every one of them graded `.husky/*` files that this route never wrote. they came from an upgrade that was already uncommitted in the worktree when the route began: rhachet 1.51.0 → 1.54.1, rhachet-roles-bhrain 0.43.1 → 0.44.1, rhachet-roles-ehmpathy 1.42.0 → 1.43.0, plus a declapract husky practice (`check.secrets.sh`, `check.timestamps.lock.sh`, a rewritten `check.timestamps.sh`, `pre-commit`, `check.nvm.sh`, `check.lockfile.sh`), `.gitattributes`, and the `.agent/.actors/…/.claude` hook dispatch manifest.

## .the gap, precisely

the upgrade is not in the trust-of-wisher-how pr. its `.husky` files are set aside, byte for byte, in that worktree at `.temp/foreign.upgrade.husky/` (gitignored); `package.json`, `pnpm-lock.yaml`, `.gitattributes`, and `.agent/.actors/*` stay uncommitted in place, since the session's own tool hooks run on them.

the review found real defects in that upgrade. each must be settled before it lands:

- **the `.eco/*` exemption is dropped.** `rule.forbid.timestamps-in-tracked-files` names `.eco/*` as an allowed home and says the gate exempts it. the new hook removes the skip and forbids any exemption, so every commit that stages a prioritizer store row halts. either restore the skip, or retire the exemption in the rule and migrate the store in the same pr
- **the secret scan fails open.** `line=$(… | grep -nIE … | head -n 1 | cut -d: -f1)` runs under `set -eu` with no `pipefail`, so a grep fault (a malformed shape) reads as no match. halt with a `💥 MalfunctionError:` on a grep status other than 0 or 1
- **an anthropic key is misnamed.** the `openai-style key` shape (`sk-…`) precedes `anthropic key` (`sk-ant-…`) and matches it first, so the halt names the wrong vendor to rotate
- **`git hash-object` is unguarded** in `check.timestamps.lock.sh`: a failed read becomes "the hook was changed", a ConstraintError with a phantom fix
- **the new halt states have no snapshot**: secrets, lock drift, and the rewritten timestamps halt
- nitpicks: positional args in `timestamps_lock_halt`; the timestamps halt lost its `fix:` line; the secret scan halts on the first leak, not all of them; inline decode-friction in both new hooks
- `cliOfRepoSettingsHooks` fails under the upgrade (hooks move into a dispatch manifest), so that test owes an update in the same pr

## .the shape of the fix

a branch off main that carries the upgrade alone: restore the six `.husky` files from `.temp/foreign.upgrade.husky/`, commit with `package.json`, `pnpm-lock.yaml`, `.gitattributes`, and `.agent/.actors/*`; settle each defect above; update `cliOfRepoSettingsHooks`; snap each halt state.

## .why it is not done in this round

it is not this route's work. the trust-of-wisher-how pr ships a behaver rule; an upgrade of the commit hooks and three dependencies inside it would be a scope leak, and its defects would hold the rule's pr hostage.
