# 🌙 dream: the driver's `onStop` hook must not fire inside an enrolled reviewer

- **kind** = reseed
- **owner** = `ehmpathy/rhachet-roles-bhrain` (`route.drive --when hook.onStop`, `rhx enroll`)
- **caught** = 2026-09-26

## .the cue that fired

stone `5.1.execution.from_vision`, peer round i014, lane `enroll-impl-arch-defects` read
`💥 malfunction` — *"review tally fallback failed"*.

## .the gap, precisely

- `rhx clone get @:fbfe599f` shows the reviewer wrote a valid review at T+9m, closed with
  `0 blockers` / `9 nitpicks`
- the clone runs in the same worktree, so it loads the same `.claude` hooks — and among them
  `rhx route.drive --when hook.onStop`, which blocks any stop until the STONE moves
- the reviewer correctly refused to move the stone; the hook re-fired for 5 more minutes
- the guard captured the final exchange — a hook prompt — so no tally reached the parser
- `FIREWORKS_API_KEY` was unlocked, so the fallback's "could not be reached" misnames the cause:
  it had no counts to tally, not no route to the model

## .the shape of the fix

`route.drive --when hook.onStop` exits `0` when the session is an enrolled reviewer, not the
driver — e.g. key on an env var `rhx enroll` sets for its child, or on the `.agent/.actors` slug.
a reviewer has no stone to move, so the hook has naught to ask of it.

secondary: the tally fallback's error should say *"no counts in the captured output"* when the model
answered, and reserve *"could not be reached"* for a transport failure.

## .why it is not done in this round

another repo. this route's guard carries a prompt-level workaround (tell the reviewer to answer a
hook with its review again), which makes the last message carry the tally but leaves the loop.
