# 🌙 dream: `rhx git.repo.get --words` returns zero matches, silently, for words that exist

- **kind** — fix
- **owner** — `ehmpathy/rhachet-roles-ehmpathy` (the mechanic's `git.repo.get` skill)
- **caught** — 2026-09-22

## .the cue that fired

a self-review at the `1.vision` stone of
`v2026_09_22.feat-lift-supervisor-and-prioritizer-roles` went to verify a symbol i had cited in a
demo (`CREWWORK_ROLES_DEFAULT`). the search returned **0 matches**, and for a few minutes i
believed i had caught myself with a fabricated citation.

then i sanity-tested the tool against a word that **certainly** exists, and it also returned 0.

## .the gap, precisely

`--words` returns **zero matches, exit 0**, for words that are demonstrably present. measured
against `sandpine/ops-notebook`, which contains files literally named `crewwork.sh`:

```
$ rhx git.repo.get files --repos 'sandpine/ops-notebook' --words 'crewwork'
   └─ found: 0 files                                    # 👎 "crewwork.sh" exists

$ rhx git.repo.get lines --in sandpine/ops-notebook \
    --paths '.agent/repo=.this/role=any/skills/work/crewwork.sh' --words 'crew'
   └─ found: 0 matches                                  # 👎 the file is named crewwork.sh

$ rhx git.repo.get lines --in sandpine/ops-notebook \
    --paths '.agent/repo=.this/role=any/skills/work/crewwork.sh'
   └─ (7026 lines, read correctly)                      # ✅ read mode works
```

⇒ **read mode works; search mode does not.** both documented forms fail — `files --repos --words`
(the readme's own example shape) and `lines --in --paths --words`.

🔴 **and the failure is silent.** `🐢 crickets...`, `found: 0`, exit 0 — which is exactly what a
true negative looks like. there is no way to tell "this word is absent" from "the search did not
run".

## .why this one bites hard

the skill's whole purpose is to check a claim against another repo. a search tool that reports
**absence** when it means **failure** does not merely fail to help — it **manufactures false
negatives**, and a false negative reads as evidence.

in this case it nearly produced a confident, wrong review finding: *"i cited a symbol that does
not exist."* the correct finding was *"i cited a symbol i cannot verify, with a tool that cannot
verify anything."*

⇒ `rule.forbid.failhide` — an operation that cannot do its job must say so, never return a clean
zero.

## .the shape of the fix

1. **diagnose** whether `--words` reaches a real search backend at all (`gh search code` has an
   indexing lag and does not index every repo; a private repo may be uncovered entirely). if the
   backend genuinely cannot serve the query, that is the fail-loud case
2. **fail loud on an unusable query** — if the backend errors, is unindexed, or is rate-limited,
   exit non-zero with the reason. never render `found: 0`
3. **distinguish the two zeros in the output** — `no matches (searched N files)` vs
   `search unavailable — <reason>`
4. **clamp it** — a test that searches a repo for a word present in a file, and asserts a non-zero
   match count. it would go red today

🟡 a cheaper interim: if `--words` cannot be made reliable, **remove it from the readme's examples**
and from the pre-approved permission list, so nobody leans on a result it cannot deliver.

## .why it is not done in this round

the SAFE/CLEAN test (`rule.always.fix-forward-under-scouts-honor`):

- **safe?** 🔴 no — the fix lands in a **different package** (`rhachet-roles-ehmpathy`'s mechanic
  skill), and the diagnosis may reach a search backend whose behavior i have not established
- **clean?** 🔴 no — it touches a repo this lift does not otherwise open

⇒ unsafe **and** unclean, so it is a deferral with no argument on the other side. no fulcrum is
owed: there is one right answer (fail loud), so this is a **defect**, not a fork.

⚠️ the deferral costs the next traveler naught **if they read this**, and costs them a false
finding if they do not — which is why the dream states the reproduction rather than the symptom.
