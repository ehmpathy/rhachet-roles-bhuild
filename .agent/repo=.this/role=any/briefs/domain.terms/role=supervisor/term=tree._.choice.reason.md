# domain.term.choice.reason: tree

## .etymology

`tree` was already this repo's word: `treework` (the lib), `git.tree.behavior`, `git.tree.del`, and
`define.work-primitive-hierarchy` (*"a TREE: worktree + branch + pr"*). short for worktree, and it
fits the garden set — a grove holds trees, a tree is sprouted (`term=sprout`).

## .why the synonyms distort

| ⛔ synonym | why it distorts |
|---|---|
| `repo` | one repo holds several trees, each with its own crew. a repo names a set, not a place |
| `branch` | a branch is a git ref; the same branch can be checked out on two groves. the tree pins it to one place |
| `worktree` | git's mechanism word. accurate, but long, and it pulls the reader to git internals |
| `checkout`, `workspace` | ide and vcs jargon with no pr or crew in the sense |

## .the evidence

found while the phone vision (`.behavior/v2026_10_21.feat-phone-text`) walked its reach × known
cells. the first address draft, quoted from #490, was `<org>/<repo>` + `@:<clone>`. the walk found a
repo with two worktrees, each with its own `@:mechanic` — so the address named two peers. a
`#<branch>` qualifier fixed the collision but named a git ref, not the place. the human asked:
*"isnt the point of bhuild that we work in <tree>s, not branches?"* and *"why even say repo"*. the
tree pins the repo and the branch at once, and is the word the supervisor already speaks.
